# Vulpes

**一个高选择性的 Hyperliquid 合约交易 Agent。** 名字取自狐属（*Vulpes*）：
狐狸耐心、善于观察、极少出手 —— 正对应它的核心立场，
**盈利来自拒绝信号的能力，而不是信号的数量**。

它最小但完整，把三件事拼在一起：

| 来源 | 借鉴的东西 |
|---|---|
| ZoneIn 多因子合成器 | 聪明钱 40% + 技术 35% + 市场 25% → 0-100 得分 → 离散信号 |
| chainstacklabs/hyperliquid-trading-bot | YAML 配置驱动、测试网默认、优雅退出、风控开关 |
| Senpi 22-Agent 实盘实验（Fox） | 选择性执行、频率上限、冷却期、趋势过滤、禁止自我调整 |

**核心立场**：策略内核不是网格，而是"高选择性 + 聪明钱对齐"。22 个 Agent 的实盘数据表明，
盈利来自**拒绝信号**的能力，不是信号的数量。

## 三因子合成

| 因子 | 权重 | 读什么 | 如何打分 |
|---|---|---|---|
| 聪明钱 | 40% | 排行榜 Top N 账户在目标币的实时持仓 | 多头名义占比，50% 为中性，放大 1.6x |
| 技术 | 35% | Supertrend / EMA / RSI / ADX（1h + 4h） | 加权混合，ADX 决定趋势可信度 |
| 市场 | 25% | 资金费率 / 持仓量 / 24h 涨跌 | 拥挤度（逆向）+ 动量，按资金费率强度调权 |

### 置信度处理

关键设计：**置信度为 0 的因子不贡献中性分 50，而是把权重让给有数据的因子。**

这意味着不会因为某个数据源挂掉就把信号稀释成"看起来中性"。代价是信号建立在更少的输入上，
所以纪律层另外强制要求聪明钱对齐，而不是单纯信任混合分。

### 聪明钱因子的选钱包逻辑

这是全项目最反复打磨的部分，结论来自实测而非直觉。

**问题**：直接取排行榜单一窗口的 top-N 是运气污染的代理变量。实测主网数据，
`week` 与 `month` 的 top-25 集合只有 **11% 重合**（Jaccard 0.111）。

**方案**：对多个窗口分别排名并取并集，用「持续性」（出现在几个窗口中）加权。

关键实测对比（BTC，同一时刻）：

| 方案 | 采样钱包 | BTC 持仓者 | 多头名义 | 最大单仓占比 |
|---|---|---|---|---|
| 单窗口 top25 | 25 | 10 | $3.8k | 43.6% |
| 并集 + 持续性**硬过滤**≥2 | 52 | **3** | — | 45.6% |
| **并集，持续性作权重** | 118 | **18** | **$149M** | **27.9%** |

**重要发现：把持续性当硬过滤条件反而有害。** 能跨窗口持续排名的钱包多为
$1B 级的大型多元账户，往往在特定币种上并无持仓；而真正持有该币种的
方向性交易者通常只出现在单个窗口里。所以持续性在这里用作**权重**
（3 窗口钱包的名义按 3 倍计），而不是筛选门槛。

净效果：持仓样本 10 → 18，单仓集中度 43.6% → 27.9%，名义金额量级恢复正常
（原来的 $3.8k vs $1.0M 是明显失真的）。

如果确实想要更小更严格的集合，把 `min_persistence` 设为 2 即可，但要接受覆盖率的损失。

以下每一条都对应 22-Agent 实验里的一个失败模式。

## 风险控制

头寸按风险预算计算，而不是固定名义金额：

```
stop_distance = 1.5 × ATR          （或 stop_loss_pct 指定的距离）
risk_usd      = equity × risk_per_trade_pct
size_by_risk  = risk_usd / stop_distance
size_by_alloc = (equity × account_allocation_pct) / price
size          = min(size_by_risk, size_by_alloc)
```

波动大的标的自动作小仓位。这是"每笔风险 2%"成为真实约束而非装饰的关键。

配置层的硬性拒绝：

- 杠杆 > 10x 直接拒绝（对应 Dire Wolf 的 25x 自杀式加仓）
- 主网实盘必须显式指定 `risk_preset`，且杠杆 ≤ 3x
- `dry_run: false` 但没有私钥 → 拒绝启动
- `safety.hard_stop_pct` 必须 ≥ `risk.stop_loss_pct`，否则安全垫会先于止损触发
- `take_profit_pct` 必须 ≥ `stop_loss_pct`，否则是负期望
- 未知配置键直接报错（拼错 `max_signals_per_day` 不会被静默忽略）

### 最大回撤保护

`risk.max_drawdown_pct` 会跟踪峰值权益，回撤触及上限时**停机且不再开新仓**。
停机状态**持久化到磁盘**，重启不能绕过 —— 否则「重启进程」就成了绕过风控的手段。

### 护栏跨重启

当日交易次数、冷却期、连亏熔断、持仓状态全部持久化在 `logs/agent_state.json`：

```bash
python run_bot.py --show-state    # 查看当前状态
python run_bot.py --clear-halt    # 解除停机（仅解决根因后使用）
```

这一条至关重要：**「限制交易频率」是本项目唯一有证据支撑的 edge**，如果重启就归零，
那等于没有护栏。

## 资金安全机制

以下每一条都对应一个真实发现并修复的缺陷，不是理论防御。

### 1. 保护单失败立即平仓

开仓后若止损单挂失败，会**立即市价平仓**。若平仓也失败，则记录该仓位（以便继续尝试管理）
并**停机**，要求人工介入。

绝不允许出现「仓位在交易所存在、程序却不知道」的裸仓。

### 2. 限价单未成交不算持仓

只检查订单返回的 `error` 是不够的 —— 未成交的挂单返回 `{"resting": ...}`。
把挂单当成成交会产生**幽灵仓位**（追踪一个不存在的敞口，之后还会「平掉」它）。

现在的流程：提交 → 解析 `filled`/`resting`/`error` → 若是 `resting` 则有界等待，
超时**撤单并放弃本次入场**，不创建 Position。

### 3. 启动时对账

启动时用交易所的真实持仓与本地状态比对，四种情况都被显式处理：

| 本地 | 交易所 | 处理 |
|---|---|---|
| 空仓 | 空仓 | 无事 |
| 空仓 | **有仓** | 孤儿仓 → 接管并告警（检查是否有保护单） |
| 有仓 | **空仓** | 幽灵仓 → 清除 |
| 有仓 | 有仓但**不一致** | 以交易所为准并告警 |

对账读取失败时**拒绝交易**，而不是当成「空仓」继续 —— 后者正是孤儿仓被忽略的原因。

### 4. 异常不再终止循环

主循环捕获所有异常并计数，连续 5 次失败则停机。此前只捕获两类异常，
其他异常会直接杀死进程。

## 数据源设计：为什么聪明钱永远读主网

**`testnet` 只控制订单发往哪里，不控制信号从哪读。**

聪明钱因子（权重最高，40%）始终从主网读取鲸鱼数据，原因是一个实测出来的 bug：
排行榜返回的是主网账户地址，但如果用测试网 API 去查这些地址的持仓，会全部返回空 ——
测试网上没有鲸鱼。这会让最高权重的因子静默归零，信号却看起来"正常"。

修复前实测：25 个钱包采样，**0 条持仓**。修复后：**10 条真实持仓**。

日志里每个信号都会标注 `data_network`，避免这个歧义再次出现。

## 性能

首次运行需要下载排行榜（**37 MB / 45,138 个账户**，接口不支持服务端限量），
因此做了两层缓存：

| 阶段 | 耗时 |
|---|---|
| 首次运行（下载 37MB + 解析） | ~28-47s |
| 后续进程（命中磁盘缓存，`logs/smart_money_wallets.json`） | **0.1s** |
| 单轮循环，冷启动（含 118 个钱包持仓读取） | ~41s |
| 单轮循环，热路径 | ~18s |

持仓读取是独立 HTTP 请求，已改为并发（12 线程）。串行 25 个钱包实测 58s，
并发后大幅缩短。多窗口并集把候选池从 25 提升到 118，代价是读数变多，
换来的是持仓样本 10 → 18 和集中度 43.6% → 27.9%。

磁盘缓存按「配置签名」校验（窗口列表、取样数、持续性阈值、白/黑名单），
配置一变缓存自动失效，不会读到过期的选择结果。

每轮 18-41s 的工作量，配合 300s 轮询间隔，占用率约 6-14%。这不是一个剥头皮机器人。

## 代码审查发现并修复的缺陷

一轮系统性审查（重点放在资金安全路径）发现并在修复前**全部有测试复现**的问题：

### 🔴 挂单永远不会被撤销（最严重）

`self._last_result` 被初始化为 `None` 却**从未被赋值**，导致 `_last_order_id()`
永远返回 `None`：

1. 限价单挂出 → 交易所返回 `{"resting": {"oid": 123}}`
2. `_resolve_resting_order` 拿不到 oid → **立即返回，既不等待也不撤单**
3. `open_position` 抛出「did not fill **and was cancelled**」

**订单从未被撤销。** 它仍挂在盘口，随时可能成交 —— 而程序认为自己空仓。
结果是**无止损、无止盈、无人管理的孤儿仓位**，日志还在说谎。`order_type: limit`
是默认配置，所以这是默认路径。

**根因是测试覆盖为零**：`resting` / `_last_order_id` / `_cancel_order` 一个测试都没有，
所以 204 个测试全绿也没抓到。现已补 `tests/test_execution.py`（26 个用例）覆盖
整条挂单生命周期。

修复后语义更严格：**只有交易所状态确认撤销，才报告为已撤销**；
撤销无法确认时抛 `CriticalExecutionError` 直接停机，而不是继续在未知敞口下交易。

### 🟡 反转平仓失败 → 旧仓位被孤儿化

`close_position` 失败时静默返回，但主循环继续开新仓并覆盖 `self.position`，
旧敞口从此无人管理。现在 `close_position` 返回布尔值，主循环在平仓失败时
**放弃本轮入场**。

### 🟡 审计日志失真

`order_filled` 事件里 `requested_size` 和 `filled_size` 都是覆盖后的值，
原始请求量丢失，无法审计部分成交。现已分别记录。

### 🟡 定仓提示与算式自相矛盾

日志输出「10% of $1,000 = $100 **at 2x**」，暗示名义价值是 $200，
但代码实际把 notional 限制在 $100。杠杆限制的是保证金而非名义价值。
现改为如实说明 notional 与所需保证金。

### 🟡 挂单参数会静默改变选币语义

`top_traders` 走旧的单窗口路径，会**静默把三窗口并集坍缩成单窗口**，
与 `top_per_window` 语义冲突。项目无外部用户，已直接移除该兼容参数
（配置写错应当显式报错，而不是静默降级）。

### 🟢 其余清理

- 删除死代码：`DEFAULT_TOP_TRADERS`、`self.top_traders`、`close_position` 中未使用的 `is_buy`
- `HyperfeedSource` 此前绕过 `http_util`，无重试/截断/体积上限保护；
  现统一走 `request_json`（新增 `headers` 参数以支持 Bearer token），
  且不再把钱包地址截断到 12 字符（那会破坏钱包身份标识）
- 魔数收敛为常量：`FALLBACK_STOP_FRACTION`、`TAKER_FEE_RATE`、`SMALL_NOTIONAL_USD`、
  `SNAPSHOT_REUSE_SECONDS`
- ATR 回退此前在 3 条路径中有 2 条静默降级，现全部记录到 notes
- R:R 提示此前只对 LONG 计算（做空缺提示）；改为对多空对称
- 修正 `_cancel_order` 的错误签名回退 —— 它曾尝试
  `cancel(symbol, (oid, symbol))`，把元组当成订单 id 传递，永远不可能成功

## 回测层审查发现并修复的缺陷

第二轮审查转向 `backtest/`（约 1900 行）。**先说结论：反未来函数的设计是正确的** ——
`BacktestMarket` 用 `bisect_left` 划定「只返回已收盘 bar」的边界，指标与因子在
bar T 的开盘时刻只看得到 T 之前的数据，成交在 T 的开盘价，这是标准的
「收盘决策 / 开盘成交」约定，不存在未来函数泄漏。这部分实现和注释都准确。

但发现了几处会**系统性美化或偏离结果**的问题：

### 🟡 止损成交价忽略跳空（会美化回测结果）

`_manage` 里止损触发时直接用 `pos.stop_price` 作为成交价。可是如果这根 bar
**开盘就已经跳空越过止损**，根本不可能在止损价成交 —— 实际成交价应该是开盘价。

```python
# 修复前：bar 从 90 开盘、止损 97，却按 97 记成交
self._close(ts, pos.stop_price, "stop loss", bar)
# 修复后
self._close(ts, min(pos.stop_price, bar.open), "stop loss", bar)   # 多头
self._close(ts, max(pos.stop_price, bar.open), "stop loss", bar)   # 空头
```

这是回测最不能出错的方向：**每次都按理想价格止损，等于高估了所有被止损的交易**。
止盈侧保持按目标价成交不变 —— 跳空穿过止盈是有利的，按目标价记反而是保守的。

### 🟡 回测置信度系统性偏离实盘

`HistoricalSmartMoney` 无法重建每个钱包的未实现盈亏（资金费历史里没有开仓价），
于是 `unrealized_pnl` 全是 0。而实盘 `evaluate` 用它算 `winner_ratio`：

```python
winner_ratio = 盈利钱包数 / 总数        # 回测恒为 0
quality_conf = 0.5 + 0.5 * winner_ratio # 因此恒为 0.5（该项下限）
```

实测偏差 **0.075**，且**足以跨越 `min_confidence` 阈值改变交易决策**。回测永远
按「所有鲸鱼都刚好不赚不亏」这个最悲观假设打分。

修复：给快照加 `pnl_available` 标记，不可知时把该项取**区间中点**而不是最小值。

我最初写的是「丢弃该项、其余权重重归一化」，**实测后发现是错的**：

| 方案 | 置信度 | 是否落在实盘区间 `[0.450, 0.525]` |
|---|---|---|
| 旧行为（当作 0 已知） | 0.4500 | 区间**边缘**（悲观端） |
| 丢弃 + 重归一化（错误方案） | 0.4412 | **区间外**，反而更偏 |
| 取中点（最终方案） | **0.4875** | **区间正中**，上下偏差对称 ±0.0375 |

丢弃一项会把权重错误地转移给不相关的因子，所以「少用一项信息」并不等于「中性」。
只有取该项自身区间的中点才是无偏的。这个教训比修复本身更值钱 ——
我差点把一个看起来合理、实测更糟的方案当成改进交出去。

### 🟡 归一化参数硬编码

`persistence_window_count=3` 是写死的，而它是 `curation_score` 的分母
（`persistence_window_count` 也是 `SmartMoneySnapshot` 的字段）。如果实盘配置
`windows` 不是 3 个，回测的 curation 与置信度就会和实盘不一致 —— 而
`engine.py` 的设计前提正是「回测与实盘走同一套决策代码」。现已从配置读取。

### 🟡 `CandleSeries` 一半公开、一半私有

容器只公开了 `closes`/`highs`/`lows`，缺 `opens`/`times`/`volumes`，
于是回测代码只能伸手取 `series._times`、`part._opens` 等私有字段（共 9 处）。
补齐公开访问器并全部改用，同时加了一条**扫描源码**的回归测试防止退回。

### 🟢 其余清理

- `funding_at_ms` 每次调用都重建时间戳列表，是 O(n) 而非注释声称的 O(log n)。
  现由 loader 构建一次索引，并让 `funding_between` 用 `bisect` 划定区间而非全表扫描
- `_try_enter` 中 `open_position`/`is_reversal` 恒为 False/0（该方法只在空仓时调用）
- `run()` 的 if/else 两个分支都调用 `set_now(ts)`，已合并

### 打分解耦：消除 `__new__` 绕过构造器

回测此前用 `SmartMoneyFactor.__new__(SmartMoneyFactor)` 造一个**半成品实例**，
再手工补上 `evaluate` 恰好会读到的那一个属性，借此复用实盘打分逻辑。

它能跑，但**没有任何测试能阻止它变脆**：一旦 `evaluate` 新增一处 `self.xxx` 依赖，
回测会在运行时抛 `AttributeError`，而实盘与全部测试依然全绿 —— 缺陷只在一个
人恰好去跑回测时才暴露。

现已把打分逻辑从 `SmartMoneyFactor.evaluate` 抽成**模块级纯函数**：

```python
def score_snapshot(snapshot, symbol=None, data_network="mainnet") -> FactorScore
```

- 纯函数：无 I/O、无实例状态，`data_network` 从实例属性变成显式入参
- `SmartMoneyFactor.evaluate` 退化为薄包装：**只负责取快照，然后交给纯函数**
- `HistoricalSmartMoney.evaluate` 直接调用同一个纯函数，不再需要任何实例
- 顺带把散落的魔数收敛为具名常量（`WEIGHT_*`、`SAMPLE_SIZE_SATURATION`、
  `LEADERBOARD_CONF_CAP_*`、`WALLET_ERROR_CONFIDENCE_PENALTY`）

**两条路径的一致性现在由结构保证，而不是靠约定**。并加了三条测试固化：

| 测试 | 保证 |
|---|---|
| `test_live_evaluate_delegates_to_the_shared_scorer` | 实盘输出与纯函数调用**逐字段相同**（score/confidence/reasons/details）|
| `test_backtest_evaluate_delegates_to_the_same_scorer` | 回测输出与纯函数调用逐字段相同 |
| `test_production_code_does_not_bypass_constructors` | 源码级扫描，`__new__(` 不得再次出现 |

这是本次审查里我认为最有价值的一处改动：它把一个**「当前正确但无保护」**的
隐式契约，变成了**「结构上不可能违约」**的显式接口。

### 已知局限（已识别，刻意未改）

这两项不是 bug，而是有意的取舍，写在这里以免被误认为已解决：

1. **回测未建模滑点。** `ASSUMED_SPREAD_BPS = 2.0` 只用于盘口价差告警，
   从不进入盈亏计算。回测的执行成本只有手续费 + 资金费。对低频策略影响有限，
   但任何"边缘很薄"的结论都应当打折扣看。

2. **入场那根 bar 的区间不参与出场判定。** `_manage` 在 `_try_enter` 之前执行，
   所以 bar T 开盘建仓后，第一次出场检查发生在 T+1。若止损在 T 之内被打穿，
   回测会继续持有 —— 实盘不会。这是双向误差，不单方向美化，但确实是偏离。

## 统一数据层（`datalake/`）

研究数据的 canonical schema。历史来自 Hydromancer 归档，前向来自 Hyperliquid
接口 —— **两套来源、两种字段命名、两种符号约定**。映射只发生一次，就在这里，
并对两个来源都做了测试。

这一层**不含任何 I/O**：不读 parquet、不连 S3、不引入第三方依赖。存储格式是
另一个决定，而这一层不应该因为它而改动。

### 六类记录

| 数据集 | 记录 | 主要来源 |
|---|---|---|
| `candles` | OHLCV（含 quote 成交量与成交笔数） | 归档 1s / 接口 |
| `funding` | 小时资金费率 | 接口 |
| `positions` | 每个钱包每个市场的持仓 | 归档日快照 / 接口 |
| `account_values` | 账户级聚合（`min_account_value` 过滤读它） | 归档 |
| `leaderboard` | 钱包滚动窗口表现（**重建**，非归档） | 由 fills 推导 |
| `orderbook` | 20 档 L2 快照 | 归档 1m / 接口 |

### 两个归档缺失、必须推导的字段

归档的持仓表**既没有 `unrealized_pnl`，也没有 `mark_price`**：

```python
mark_price     = notional / size                 # 两者都带符号，符号相消
unrealized_pnl = notional - size * entry_price    # 等价于 (mark - entry) * size
```

一个表达式同时覆盖多空：空头时 `notional` 与 `size` 同为负，减法仍然成立。

**为什么推导而不是存储**：接口自带 `unrealizedPnl`，但若前向存原值、历史存推导值，
两段就不可比 —— 而「把两段放在一起比较」正是这件事的全部意义。
测试用**接口自报的 PnL 反查推导值**，而不是自证。

> 这同时也是第二轮审查发现的「回测置信度系统性偏离实盘 0.075」的根源：
> 当时 `unrealized_pnl` 恒为 0，`in_profit_pct` 永远算错。推导补上，偏差即消失。

### 符号归属在入口消除歧义

归档文档说明 `size` 正=多、负=空，但**没有说 `notional` 是否带符号**。这个歧义
必须在边界解决，因为两个推导式在符号错误时会**静默反向** —— 空头会被报成亏损，
而不抛任何异常。

所有适配器统一走 `signed_notional()`，因此无论来源如何编码，落库记录都无歧义。
测试覆盖「归档已带符号」与「归档只给数值」两种编码，要求产出**完全相同**的记录。

### 有意保留的防护

- 单字母键（`o/h/l/c`）容易转置，而转置后的 K 线看起来仍像正常 K 线 ——
  适配器校验 `low ≤ open/close ≤ high`，不合法直接抛错
- 钱包地址统一小写，避免同一钱包被拆成两个身份
- 非有限浮点（`nan`/`inf`）一律拒绝，与 `agent/state.py` 同样的理由
- 订单簿**不做补档**：补出来的档位会被滑点模型当成真实挂单量
- `to_row()` **不写入推导字段** —— 否则今天的公式会被冻结进历史数据

### 验证

37 个测试，并用**运行时变异**确认它们承重（不是只看通过）：

| 变异 | 捕获 |
|---|---|
| `unrealized_pnl` 对空头取 `abs(size)` | 6 个测试失败 |
| `unrealized_pnl` 丢掉 `notional` 项 | 11 个测试失败 |
| `mark_price` 对 notional 取绝对值 | 3 个测试失败 |
| 归一化不再强制符号 | 5 个测试失败 |

### 一处必须先处理的问题

探测时 `aws sts get-caller-identity` 返回的是**根账号**（`arn:aws:iam::…:root`）。

一旦泄露无法用策略限制。建议改用仅授予 S3 读取权限的受限 IAM 用户。

### 列裁剪实测：fills 从 163 GB 降到 18 GB

`parquet_metadata` 给出每个列块的**精确压缩字节数**（读自文件 footer，不是估算）。
按「查询真正需要的列」求和，得到列裁剪的下限。下表的源大小是**全量真实求和**
（`--dry-run` 列出的每一个对象），不是「采样一天 × 分区数」：

| 数据集 | 全量 | 需要的列 | 裁剪后 | 省 |
|---|---|---|---|---|
| candles | 10.68 GB | 7 / 13 | 7.63 GB | 29% |
| positions | 5.09 GB | 5 / 11 | 3.66 GB | 28% |
| orderbook | 0.31 GB | 4 / 4 | 0.31 GB | 0%（按币种分文件，已在路径层省下） |
| account_values | 15.73 GB | 3 / 7 | 15.36 GB | 2% |
| **fills** | **127.58 GB** | **3 / 27** | **14.31 GB** | **89%** |
| **合计** | **159.39 GB** | | **41.27 GB** | **74%** |

**fills 独占归档的 80%，而它可压缩性最高。** 原因很直白：`tx_hash`（109 MB，26%）
与 `client_order_id`（70 MB，17%）等**纯标识符**占了 57%，而重建排行榜只需要
`address` + `timestamp` + `realized_pnl`（合计 47 MB = 11.2%）。

**裁剪后整个归档 41.27 GB，落在每月 100 GB 免费额度内 → 传输费 $0。**
不裁剪则是 159.39 GB、单月 $6.77。

> 早期版本用「采样一天 × 分区数」外推，得出 214.60 GB / 63.58 GB。全量真实列举后
> 发现外推**偏悲观**（采样日恰好高于均值）。上表是修正后的数字。

### 行组剪枝：一半可行，一半不可行

| 列 | min/max 统计 | 能否剪枝 |
|---|---|---|
| `timestamp` | ✅ 有（行组按约 6 小时切分） | ✅ 能 |
| `coin`（candles） | ❌ NULL | ❌ **不能** |
| `address`（fills） | ❌ NULL | ❌ **不能** |

所以 `WHERE coin IN ('BTC','ETH','SOL')` **不会减少任何传输** —— 过滤发生在字节
到达本地之后。**只有列裁剪有效。** 这个事实决定了同步脚本应按列裁剪组织，
而不是指望按币种过滤。

### 一处未能完成的测量，如实记录

原计划要**实测**而非推算，但两种手段在本机都失效了：

1. **`/proc/net/dev` 差值**：用已知 33.2 MB 的文件做对照，网卡读到 **95.6 MB（2.88 倍）**
   —— 本机有代理转发流量，无法隔离单次查询
2. **DuckDB 的 HTTP 日志**：记录了 `Range` 头，但**不完整**（一次全文件扫描只记录到 2 个区间）

因此上表数字来自 parquet footer 的**列级精确值**，是「查询必须读取」的上限。
方向上是可靠的，但**不能声称已经网络实测**。

### 顺带查清的两个环境问题

**1. `aws login` 的凭证 DuckDB 读不到。** 本机凭证来自 `aws login`（存于
`~/.aws/login/`），**没有 `~/.aws/credentials` 文件**，所以 DuckDB 的凭证链
（环境变量 → credentials → config）解析失败：

```
AccessDenied: Anonymous users cannot invoke requests against Requester Pays buckets
```

可行的桥接：

```bash
eval "$(aws configure export-credentials --format env)"
duckdb ...
```

但它依赖登录会话（临时凭证，会过期）。**建一个带长期访问密钥的受限 IAM 用户才是
正解** —— 也正是之前那条安全建议。现在它从「最佳实践」升级成了「阻塞项」。

**2. DuckDB 不会自动读取 `~/.aws/credentials`。** 即使有该文件，也需要
`CREATE SECRET (TYPE S3, PROVIDER credential_chain, ...)` 或环境变量，否则 Region
会解析为空、请求变成匿名。

## 同步脚本（`sync_reservoir.py`）

把归档拉进本地 `data/canonical/`。三条设计约束：

**1. 只按列裁剪下载。** 上一节测出「按币种过滤省不了任何传输，列裁剪省 70%」，
所以脚本直接生成投影查询：

```sql
COPY (
  SELECT address, timestamp, realized_pnl
  FROM read_parquet(['s3://.../fills.parquet'])
) TO 'data/canonical/fills/date=2026-09-16.parquet'
  (FORMAT PARQUET, COMPRESSION ZSTD);
```

**2. 可断点续传。** 已存在的日期文件直接跳过，中断后重跑即继续 ——
一次 63 GB 的下载不可能一口气跑完。

**3. 花钱前先报账。** 先列举、算出预估传输量与费用，然后：

- `--dry-run` 只出计划
- `--max-gb`（默认 100）超过就**拒绝启动**，而不是先花了再说

```bash
python sync_reservoir.py --dry-run                # 计划与费用
python sync_reservoir.py --datasets positions     # 先拉最便宜的高价值集
python sync_reservoir.py --limit 30 --max-gb 40   # 有界的第一轮
```

### 三档列集，默认取中间

`--columns research|wide`。默认 `research` 是回测当前需要的列；`wide` 额外保留
除**纯标识符**外的全部列：

| 数据集 | research | wide | 丢弃的 |
|---|---|---|---|
| candles | 7 列 | 13 列 | — |
| positions | 5 列 | 11 列 | — |
| account_values | 3 列 | 7 列 | — |
| fills | 3 列 | 22 列 | `tx_hash`、`client_order_id`、`order_id`、`trade_id`、`builder`、`twap_id` |

被丢弃的 6 列全是标识符，对任何指标研究都无价值，却占 `fills` 的 57%。

**先取窄集不是单向门**：整个归档都在免费额度内，将来要更多列重新拉一次几乎不花钱。

### 凭证：一处会咬人的设计缺陷（已修）

脚本原本假定 DuckDB 能自己找到凭证，实际上：

- DuckDB **不会**读取 `~/.aws/credentials`
- 更不认识 `aws login` 的会话存储

结果是匿名请求，S3 报 `Anonymous users cannot invoke requests against Requester
Pays buckets`。现在脚本先通过 `aws configure export-credentials` 解析凭证，
再以**环境变量**（而非命令行）传给 DuckDB 子进程。

⚠️ 但这依赖登录会话，**会过期**：

```
Error loading login session token: Please reauthenticate with 'aws login'
```

**长期运行必须使用带固定访问密钥的受限 IAM 用户**，否则每次会话过期都要人工介入。

### 分页列举需要重试

列举 5 万个 key 意味着几十次连续请求，而这条链路上
`SSL: UNEXPECTED_EOF_WHILE_READING` 是常态。脚本现在**只对传输类错误重试**，
凭证/权限错误立刻抛出 —— 后者是确定性的，重试没有意义，只会掩盖问题。

### 首次实跑暴露的三个缺陷

**1. 0 字节文件会被永久跳过（最严重）。** 一次卡住的 COPY 会在目标路径留下
`date=2025-07-30.parquet`（0 字节），而断点续传只检查「文件是否存在」。
结果是：**中断过的运行会静默产生带空洞的仓库，而空洞从计划里看不出来**
——它会一直把那些天报告为「已获取」。

修复：`completed_file()` 要求文件非空；COPY 改为**写临时名再改名**
（DuckDB 会先创建输出文件再读数据，所以直接写最终路径必然留下半成品）。

**2. 卡顿会永久阻塞整队。** 一次卡住的 COPY 让 `duckdb` 挂了几分钟不产出任何东西。
修复：每次 COPY 加超时与重试。

**3. 读取慢 3.4 倍（调优后解决）。** 实测读同一个 13 MB 对象：

| 配置 | 耗时 |
|---|---|
| 默认 | 85s |
| **`enable_http_metadata_cache` + `threads=8`** | **25s** |

`enable_http_metadata_cache` 避免 DuckDB 每次引用都重取 footer；`threads`
让不同列块的 range 请求并行而不是排队。

> 期间还有一次诊断反转：`ps` 显示 `duckdb` 占 99.2% CPU，我据此判断是**计算**
> 问题；但同一命令另一次运行只用了 0.56s CPU —— 说明它时而 CPU 密集、时而 I/O
> 等待。**单一时刻的采样不足以定性**，是后面的计时才把真相定下来。

## 换信息源：真实持仓（第一个符号稳定的因子，但还不是信号）

价格衍生的指标全部测尽且无效，于是转向**非价格信息**。手上有两个归档：
`positions`（逐钱包持仓快照）和 `fills`（逐钱包成交）。

### 先说一个把路堵死的发现

**`fills` 只有三列：`address, timestamp, realized_pnl`。** 没有方向、没有数量、
没有币种（它同步的是 `perp/all`，所有币混在一起）。所以「净流入」「买卖压力」
「主动成交方向」这类信号**用这份数据做不出来** —— 不是没做，是字段不存在。

### 再说一个会浪费时间的结构性陷阱

`positions` 的**名义多空比恒等于 50%**：

| 市场 | 多头名义 | 空头名义 | 多空比 |
|---|---|---|---|
| BTC | 1357.6M | −1357.6M | **50.0%** |
| ETH | 1155.0M | −1155.0M | **50.0%** |
| SOL | 266.3M | −266.3M | **50.0%** |

**每天都是 50.0**。这不是市场观察 —— 永续合约里每张合约都有多空两方，
所以**全体账户的多头名义必然等于空头名义**，这个比值恒为 1、零信息量。
按名义算的「多空比」是个诱人的死路。

### 有信息量的是「按账户数」算的多空比

```
BTC 账户数多空比:  最小 47.4%  中位 57.9%  最大 70.3%  标准差 4.18  (364 天)
```

它确实在变。测它与未来 24 根 bar 收益的关系（快照按「严格早于当日」对齐，无前视）：

| 窗口 | 标的 | corr | 低分位（人群看空）收益 | 高分位（人群看多）收益 |
|---|---|---|---|---|
| P1 2025-08~10 | BTC | **−0.0967** | +0.087% | −0.376% |
| P1 | ETH | **−0.1685** | +0.355% | −1.794% |
| P1 | SOL | **−0.1579** | +1.189% | −1.156% |
| P2 2025-12~04 | BTC | **−0.0867** | +0.574% | −0.075% |
| P2 | ETH | **−0.1053** | +0.534% | −0.232% |
| P2 | SOL | **−0.1454** | +1.428% | −0.136% |
| P3 2026-06~09 | BTC | **−0.1367** | +0.855% | +0.078% |
| P3 | ETH | **−0.0631** | −0.054% | −0.072% |
| P3 | SOL | **−0.0380** | +0.896% | +0.372% |

**9 个「窗口×标的」组合全部为负。** 这是整个项目里第一个符号稳定的预测因子 ——
对比之下，混合分数在 −0.021 ~ +0.019 之间翻转，所有技术指标都翻转。

方向和经典预期一致：**反向**。人群看空时未来收益为正，人群看多时为负。
量级也比之前找到的任何一个大 5–10 倍。

### 但它还不是信号，两个理由

**1. 简单规则不敌买入持有。** 用滚动 30 天 z 分数（无自由参数、无前视）：

| | 12 组平均 |
|---|---|
| 买入持有 | −3.20% |
| 反向 `z < −1` 做多 | **−3.50%**（更差） |
| 始终反向 | +2.40% |

「始终反向」的 +2.40% 看着不错，但个体差异极大（**+72.21% 到 −33.36%**）——
它大部分时间在做空，而 P1 恰好是下跌窗口。这是**市场状态运气**，不是信号。

**2. 分位结构不单调。** 把分位和时间尺度放在一起看：

| 多空比分位 | +4h | +24h | +72h |
|---|---|---|---|
| **Q1（人群最空）** | **+0.052%** | **+0.423%** | **+0.908%** |
| **Q2** | **−0.052%** | **−0.436%** | **−0.830%** |
| Q3 | +0.004% | +0.118% | +0.154% |
| Q4 | +0.038% | +0.191% | +0.043% |
| Q5（人群最多） | −0.044% | −0.250% | −0.068% |

Q1 最好、Q5 为负，符合反向预期 —— 但 **Q2 是最差的一档，比 Q5 还差**。
相邻两档摆动 1.7 个百分点，这不是一个干净的梯度，更像**尾部效应**或
某个未受控的因素，而不是「人群越看多、未来越差」的连续关系。

**所以正确的定位是：一个有稳定符号的线索，不是一个可用信号。**

### 这一节的保留

- 这是**探索性**分析。我先试了名义多空比（死路）、再多空比分位、再规则检验、
  再分位×尺度。多次尝试会放大「看起来有东西」的概率。
- `positions` 有 **52 天缺口**（2025-10-25 → 12-14），所以窗口选择被限制，
  四个窗口里有三个是围绕缺口挑的。
- 快照是**日级**的，做不出日内信号；所有结果都建立在「昨日持仓 → 今日收益」上。

### 深挖之后：那个 IC 站不住

顺着上一节留下的两个疑问往下查，结果推翻了上一节的强度。

**先修一个我自己埋的 bug。** 上一节分位表用的是**全样本分位**
（`allvals = sorted(整个序列)`），含前视 —— 真实交易中拿不到。而且它可能就是
Q1 好 / Q2 差那个怪形状的来源。

**1. 去趋势后相关性塌掉。** 换成滚动 30 天 z 分数（无前视）：

| 量 | 相关系数 |
|---|---|
| corr(多空比 **原始水平**, 未来24h) | **−0.10 ~ −0.17**（上一节的数） |
| corr(多空比 **滚动 z**, 未来24h) | **−0.0180** |
| corr(多空比**变化**, 未来24h) | −0.0165 |
| corr(过去24h, 未来24h) | +0.0289 |
| corr(过去24h, 多空比 z) | +0.0242 |
| 偏相关(多空比 z, 未来24h \| 过去24h) | **−0.0187** |

**那个强 IC 来自多空比的「低频水平」，不是它相对自身近期均值的偏离。**
去趋势恰好移除了那个分量，剩下的高频部分几乎没有信息。

偏相关几乎不变（−0.0187 vs −0.0180）说明：这点残存的信息**确实不是价格
代理** —— 多空比与近期价格只相关 0.024。信息独立，但太弱。

**2. 但真正致命的是有效样本数。** 账户多空比是个极慢的序列：

| 标的 | 天数 | lag-1 自相关 | lag-14 | **有效独立样本** |
|---|---|---|---|---|
| BTC | 364 | 0.8779 | 0.6443 | **24** |
| ETH | 364 | 0.9210 | 0.6641 | **15** |
| SOL | 364 | 0.8877 | 0.4117 | **22** |

有效样本 = `n × (1−ρ₁)/(1+ρ₁)`。

**「9 个窗口×标的组合全部为负」根本不是 9 次独立检验** —— 序列几乎不动，
那些数字是同一批 regime 的重复读数。**有效独立样本只有 15–24 个**，
此时相关性的标准误约 0.22，而 IC 只有 −0.10 ~ −0.17：**不到一个标准误。**

符号一致看起来很可信，是因为**同一段行情被数了九遍**。

### 这个项目真正的瓶颈

把两轮的结果并排看，问题的性质就清楚了：

| 信号类别 | 样本量 | 符号稳定性 | 有效独立观测 |
|---|---|---|---|
| OHLCV 指标（分数、Supertrend、EMA…） | 12,168 ~ 21,384 | **翻转** | 数万（但无信息） |
| ADX | 21,384 | 稳定 | 数万（规则检验失败） |
| 账户多空比 | 21,384 | 稳定 | **仅 15–24** |

**一类信号样本多但没信息，另一类有稳定性但没独立样本。**

而 414 天的归档，无论怎么切，能提供的**独立市场 regime 大约就是几十个**。
这不是加数据能解决的 —— 这是标的数量和时间跨度的问题。

所以「换信息源」这一步的结论不是「找到了新信号」，而是：

> **在现有数据规模下，任何依赖多周尺度的信号都无法被证实或证伪。
> 而高频信号虽然样本充足，却已被逐类证明不含信息。**

### 那个 Q1/Q2 的怪形状：不再重要了

原本想解释「为什么 Q1 最好、Q2 最差」。但在有效样本只有 15–24 的序列上，
分位表里相邻档位摆动 1.7 个百分点**本来就该被视为噪声** —— 去追它是在拟合噪声。
这一项从待办里划掉。

### 下一步（如果继续）

1. **扩大横截面**而不是延长时间 —— 同样的 414 天，把标的从 3 个扩到 30 个，
   有效样本就能上一个量级。这是唯一能真正提升统计功效的方向。
2. 在扩大之前，**不要再对这套数据做新的信号搜索** —— 每一次搜索都在
   15–24 个独立观测上做多重比较，找到「显著」几乎是必然的。

### 扩大横截面之后：效应确实存在，但在可交易的那一半之外

归档里能用于横截面的标的有 **161 个覆盖 350+ 天**（candles 里 882 个币/天）。
3 个标的扩到 161 个，是这一轮唯一真正的功效来源。

**方法上的关键**：时序 IC 在少数标的上被市场 beta 主导（这就是「牛市窗口 vs
熊市窗口」反复干扰结论的根源）。**横截面 IC** 每根 bar 内先去掉共同因子再算
排序相关，每根 bar 给一个独立观测 —— 有效样本从 15–24 跳到 **250–500**。

**先测经典动量/反转（25 个流动标的）：全部 |t| < 1。** 但 25 个标的的
每-bar IC 噪声太大，于是换成全部 161 个：

| 横截面信号 | 有效 N | 平均 IC | **t 值** |
|---|---|---|---|
| **mom_24h** | 464 | **−0.0410** | **−4.07** |
| mom_72h | 320 | −0.0346 | −2.83 |
| mom_168h | 304 | −0.0313 | −2.62 |
| **vol_72h** | 284 | **−0.0456** | **−3.33** |
| vol_168h | 266 | −0.0419 | −3.10 |

**两个经典效应出现了**：短期**反转**（t = −4.07）和**低波动溢价**（t = −3.33）。
而当前策略是**趋势跟随**（Supertrend、EMA 交叉）—— 方向是相反的。

**然后是决定性的检查。**「25 个流动标的测不出、161 个能测出」本身就是警告，
所以按成交额中位数把标的池切成两半：

| 信号 | 子集 | 有效 N | 平均 IC | **t 值** |
|---|---|---|---|---|
| mom_24h | **流动（81 个）** | 484 | −0.0121 | **−1.07** |
| mom_24h | 非流动（80 个） | 523 | **−0.0672** | **−5.86** |
| vol_72h | **流动（81 个）** | 286 | −0.0165 | **−1.03** |
| vol_72h | 非流动（80 个） | 333 | **−0.0879** | **−6.02** |

**在流动的一半里什么都测不到（t ≈ −1.0）。效应完全来自非流动的一半。**

**再排除最可能的替代解释。** 非流动标的上的短期反转，最常见的解释是
**买卖价差跳动** —— 成交价在买卖价之间跳动，制造出虚假的反转。
价差跳动在 1–2 根 bar 内就抵消，所以看它在更长持有期上是否衰减：

| 信号 | 持有 | 有效 N | IC | t |
|---|---|---|---|---|
| mom_24h | 24h | 517 | −0.0676 | −5.85 |
| mom_24h | **7 天** | 324 | **−0.0550** | **−4.76** |
| mom_72h | 24h | 397 | −0.0781 | −6.07 |
| mom_72h | **7 天** | 138 | **−0.0814** | **−4.46** |
| mom_168h | 24h | 345 | −0.0668 | −4.93 |
| mom_168h | **7 天** | 90 | **−0.0987** | **−4.39** |

**效应不衰减**，在 7 天尺度上反而略强（mom_168h → 7 天 是 −0.0987）。
**价差跳动被排除。**

### 这是目前唯一一个统计上站得住的东西

| | 有效样本 | t 值 | 是否可交易 |
|---|---|---|---|
| OHLCV 时序信号 | 数万 | 符号翻转 | — |
| 账户多空比 | **15–24** | 不到 1 | — |
| **横截面反转（非流动）** | **90–523** | **−4.4 ~ −6.1** | **需要另做成本检验** |
| 横截面反转（流动） | 484 | −1.07 | 无效应 |

**但要装上必须跨过三道坎，现在都还没跨：**

1. **成本。** 这是日频调仓的多空组合，每次换手付 7bp/腿 × 2 腿。
   IC 0.067 对应多少净收益**必须实测**，不能按经验估。
   我上面没有算成本 —— 这是结论里最大的空白。
2. **幸存者偏差。** 标的要求「350+ 天覆盖」，而**退市的币拿不到这个覆盖**，
   于是被排除在外。加密市场里退市币的收益是灾难性的，排除它们会**系统性
   高估反转效应**（本该continue下跌的标的被剔除了）。这个偏差当前无法用
   现有归档修正，因为退市币的 bar 本来就不全。
3. **架构不匹配。** 现有策略是**单标的、单持仓、方向性**的
   （`max_open_positions: 1`）。横截面反转需要**同时持有多空一篮子**。
   这是重写组合层，不是调参数。

### 三道坎：成本、退市、随机基准 —— 全部通过

#### 第一道：成本。**通过。**

非流动子集（80 个标的）、等权多空各 1/5、单腿 3.5bp：

| 调仓 | 信号 | 毛收益 | 成本 | **净收益** |
|---|---|---|---|---|
| 7 天 | 7 天 | +90.41% | +3.20% | **+84.47%** |
| 3 天 | 3 天 | +201.03% | +7.39% | **+179.75%** |
| 1 天 | 1 天 | +156.05% | +21.95% | +105.66% |

滑点敏感性（调仓 7 天 / 信号 7 天）：0bp **+90.41%** → 10bp +73.91% →
20bp +58.82% → **50bp 仍有 +20.85%**（50bp 是配置假设的 14 倍）。

**成本吃不掉它。** 对照组也干净：同样规则在**流动子集**上是 **−55.88%** ——
效应不存在的地方它就亏钱。

#### 第二道：退市。**通过。**

「350+ 天覆盖」的要求排除退市币，而这个策略**买入下跌者** —— 退市正是它最痛的
情形，所以偏差方向对策略有利。用「第 60 根 bar 时存在的全部标的」（171 个，
无覆盖天数要求，无前视）重做，其中 **23 个后来数据中断**：

| 持有 | 信号 | 中断按 −50% | **中断按归零** | 中断次数 |
|---|---|---|---|---|
| 7 天 | 7 天 | +97.93% | **+87.20%** | 7 |
| 3 天 | 3 天 | +91.27% | **+78.05%** | 10 |

即使**每次中断都按归零计**，仍有 +87%。顺带核实：标的池并不缺崩盘标的，
148 个里 **57 个跌超 80%**、中位跌幅 **−75%**。

#### 第三道：随机基准。**通过。**

这个项目里每个结论都是被随机对照推翻的。在一个**中位标的跌 75%** 的市场里
做多空五分位，会不会只是「在做空山寨币」？用同一票池、同一调仓、同一成本
跑 30 次**随机**多空五分位：

| 持有 | 信号 | 反转规则 | 随机 30 次中位 | 随机范围 | **百分位** |
|---|---|---|---|---|---|
| 7 天 | **7 天** | **+87.20%** | −6.60% | −59.75% ~ +64.65% | **100** |
| 3 天 | 7 天 | +78.05% | −0.12% | −48.76% ~ +92.10% | **97** |
| 3 天 | 1 天 | +86.32% | −0.12% | −48.76% ~ +92.10% | 97 |
| 7 天 | 1 天 | +7.37% | −6.60% | −59.75% ~ +64.65% | **70** |

**随机组合的中位是 −6.6% ~ −0.1%** —— 「只是做空」被排除。7 天信号下反转规则
**超过全部 30 次随机**。

还有一项顺带检查：效应是否依赖少数极端期。按均值平均 +1.22%、按中位数平均
+1.15%，两者接近，最好一期 +10.1% 最差 −9.3% —— **不是靠几期暴赚**。

### 五项挑战全部通过

| 检验 | 结果 |
|---|---|
| 成本（含 50bp 滑点） | **通过** |
| 流动子集对照 | **干净**（同规则亏 −55.88%） |
| 极端期依赖 | **通过**（均值 ≈ 中位数） |
| 退市最坏情况 | **通过**（按归零仍 +87%） |
| 随机多空对照 | **通过**（7 天信号 100 百分位） |

**这是整个项目里第一个通过全部稳健性检验的结果。**

### 但仍要守住的四点

1. **样本只有一个 414 天区间。** 效应可能不再持续 —— 这没法用现有数据回答。
2. **架构不匹配。** 现策略是单标的、单持仓、方向性（`max_open_positions: 1`）。
   这是**同时持有多空一篮子**，要重写组合层，不是调参数。
3. **IC 绝对值不大**（0.067 ~ 0.099）。那个 +87% 来自横截面离散度极大
   （p10 −89%，max +783%），不是来自强预测力。离散度一收窄，收益会大幅缩水。
4. **归档自身的完整性未验证。** 23 个标的「数据中断」说明归档保留了退市标的
   的历史，但如果有些标的的数据在退市时被整体丢弃，那部分损失就看不见。
   我按「归零」给了最坏边界，但这假设的是「数据缺了、标的死了」，
   而不是「标的死了、数据也从未进过归档」。

### 结论

**「换信息源」这一步的结果是：价格衍生指标全部无效，但横截面反转
（在流动性较差的一半市场、7 天尺度上）通过了成本、退市、随机基准三重检验。**

这不是一个可以立刻上线的信号 —— 它需要的组合架构与现有代码完全不同。
但它是这个项目里第一个**没有被数据推翻**的东西。

## 策略调整：ATR 止损有效，追踪止损无效

按要求把核心组合改为 **1H EMA20/50 + RSI(14) + ADX(14)>20 + 量能确认**，
止损 2×ATR(14)，追踪止损 1.5×ATR。逐步实现并逐步测量（170 天 × 3 币种）：

| 累积改动 | 交易 | PF | 收益 | 随机百分位 |
|---|---|---|---|---|
| 原配置（EMA21/55，无门槛，3% 固定止损） | 119 | 1.21 | +4.87% | 0/0/10 |
| + EMA 20/50 | 117 | 1.23 | +5.26% | 0/0/30 |
| + ADX>20 与量能确认 | 112 | **1.05** | **+1.17%** | 0/0/60 |
| + 2 ATR 止损 | 130 | **1.32** | **+5.30%** | **70/20/80** |

**净改善全部来自 ATR 止损**（1.05 → 1.32）。EMA 20/50 中性。两个门禁是负贡献 ——
去掉后 PF 1.32 → 1.41、收益 +5.30% → +6.65%。

### 追踪止损：实现了，测了，关掉了

**这是唯一没有按指令保留的一项。** 每一种追踪配置都比不开更差：

| 追踪设定 | 交易 | PF | 收益 | 离场构成 |
|---|---|---|---|---|
| **关闭** | 130 | **1.32** | **+5.30%** | stop:95 take:23 reversal:11 |
| 1.5A 生效 0A | 328 | 0.86 | −2.81% | **stop:326 take:1** |
| 1.5A 生效 0.5A | 315 | 0.92 | −1.59% | stop:313 take:1 |
| 1.5A 生效 1.5A | 288 | **0.80** | **−4.86%** | stop:286 take:1 |
| 3.0A（比止损宽） | 199 | 1.02 | +0.48% | stop:187 take:11 |

机制写在 `take` 那一列：**追踪在 1.5 ATR 处离场，9% 的止盈几乎永远够不到
（23 笔塌到 1 笔）**。而 `max_open_positions: 1` 意味着每次离场都释放仓位槽
—— 交易数翻 2.8 倍，正是本项目自身证据里说最危险的那个变量。

**触发它的一个设计缺陷**：1.5 ATR 的追踪比 2 ATR 的止损**更紧**，所以它在入场
第一根 bar 就接管了，**2 ATR 的止损从未起过作用**。加了
`trailing_activation_atr_multiple` 可以推迟它，但生效时机也救不回来。

### 为什么门禁保留、追踪关闭

判断依据是**测量是否超出噪声带**，而不是「有没有变差」：

- **追踪止损**：PF 1.32 → 0.86，交易数 2.8 倍，326/328 全是止损离场。
  这是**机制被换掉了**，不是噪声。
- **两个门禁**：PF 1.32 → 1.41，全部落在此前测定的噪声带 `[0.80, 1.82]` 内。
  **测不出结论就不擅自改**，按原设计保留。

### 仍然成立的老结论

最终配置 **PF 1.32、+5.30%**，依然**跑输买入持有**（+14.61% / +20.85% / +19.00%），
随机百分位 70/20/80 也谈不上优势。**这不是一次胜利，只是把入场侧又调了一遍。**

## 入场信号的诊断：分数不含信息量

离场也排除了，于是转向入场。但在改之前先回答一个更基本的问题：
**现有分数和未来收益到底有没有关系？** 没有的话，改权重就是白费。

做法：逐 bar 算分（复用 `Synthesizer`，不交易），取未来 24 根 bar 的收益，
看两者的相关性。三个不重叠窗口（各 100 天 × 3 币种）：

| 窗口 | 样本 | corr(score, 未来收益) | 多区胜率 |
|---|---|---|---|
| W1 2025-08~12 | 7128 | **+0.0192** | 48.7% |
| W2 2025-12~04 | 7128 | **−0.0214** | 44.0% |
| W3 2026-06~09 | 7128 | **+0.0023** | 51.1% |

**相关系数在窗口之间翻转符号，均值约为 0。做多区胜率始终在 50% 附近。**

分位表（W3 窗口）也完全不单调 —— 60-70 与 70-80 的未来收益（+0.041%、+0.021%）
**低于** 40-50（+0.194%）。也就是说分数越高，未来收益并不越好。

### 分解到组件：没有一个指标有稳定信息

| 预测因子 | W1 corr | W3 corr |
|---|---|---|
| 当前分数（混合） | +0.0192 | +0.0023 |
| 技术因子分 | +0.0295 | **−0.0075** |
| Supertrend 1h 方向 | +0.0407 | **−0.0175** |
| Supertrend 4h 方向 | **−0.0149** | +0.0066 |
| **ADX(14) 水平** | **+0.0940** | **+0.1405** |
| RSI(14) 水平 | +0.0152 | +0.0288 |
| EMA21/55 价差 % | **−0.0617** | +0.0373 |
| 动量 24 根 | +0.0056 | +0.0455 |

**除 ADX 外全部翻转符号。** 而值得注意的是：ADX 在当前配置里的权重是
技术因子的 0.15 × 总权重 0.35 ≈ **总分的 5%** —— 唯一有信号的输入被分到了最小的权重。

### 但 ADX 也扛不住留出检验

ADX 是**趋势强度**、不含方向，所以它更像「择时参与」而非多空信号。
合并三个窗口（21,384 样本）后 IC = **+0.0478**（比单窗口弱，说明部分有窗口特异性），
分位结构是：

| ADX 分位 | 样本 | 未来收益均值 | 胜率 |
|---|---|---|---|
| 6.9–17.3 | 4277 | −0.047% | 50.3% |
| 17.3–22.2 | 4278 | −0.331% | 48.7% |
| 22.2–27.4 | 4278 | −0.141% | 49.2% |
| 27.4–35.6 | 4278 | −0.166% | 50.2% |
| **35.6–76.8** | 4277 | **+0.189%** | **53.4%** |

只有最高分位为正。于是试了一条最简单的规则：
**ADX > 35 且 Supertrend 1h 上行时做多，否则空仓。**

| 窗口 | 买入持有 | ADX>35 | **ADX>35 + ST上行** |
|---|---|---|---|
| W1 2025-08~12 | −35.12% | −1.26% | **+4.21%** |
| W2 2025-12~04 | −29.52% | −15.28% | −1.74% |
| W3 2026-06~09 | +35.23% | +19.10% | +12.16% |
| 平均（**样本内**） | −9.80% | +0.85% | **+4.88%** |

**`35` 这个阈值是从同一批数据的分位里挑的，所以上表是样本内。** 用一个
完全未参与选择的窗口（2026-04-01 → 06-07）验证：

| 窗口 | 标的 | 买入持有 | ADX>35 | ADX>35 + ST上行 |
|---|---|---|---|---|
| H 2026-04~06 | BTC | −8.36% | −15.70% | −6.00% |
| | ETH | −22.41% | −23.23% | −11.27% |
| | SOL | −19.38% | −22.85% | −5.58% |
| **平均（样本外）** | | **−16.72%** | **−20.59%** | **−7.62%** |

**样本内 +4.88% → 样本外 −7.62%。规则没有通过留出检验。** `ADX>35` 单独使用
甚至比买入持有更差。

### 两个附带的重要发现

**1. 我之前的「买入持有 +14.61%」是一个牛市窗口的特例。** 跨窗口看，
买入持有平均是 **−9.80%**（W1 −35%、W2 −30%、W3 +35%）。之前把它当作
「策略跑输的基准」，隐含假设了市场上涨 —— 这个假设不成立。

**2. 有一条性质是稳定复现的：`ADX>35 + ST上行` 在 6 个「资产×窗口」组合里
全部优于买入持有**（3 个样本内 + 3 个留出）。但它优于买入持有的方式是
**少亏**，不是赚钱 —— 它在下跌市里依然是负收益。

### 结论

**入场信号的问题不是权重配比，是信息源。**

- 现有分数 IC ≈ 0，且符号在两个窗口间翻转
- 所有技术指标（Supertrend、EMA、RSI、动量）的 IC 都翻转符号
- 唯一稳定的 ADX 是**强度/状态**变量，且转化为规则后留出检验失败

所以「调配比」「换周期」都被测过并且无效。要继续，需要**换一个信息源**
（不是 OHLCV 衍生的指标），或者接受一个不同的目标（控制回撤而非追求收益）。

## 离场扫描：五种配置，没有一种能翻盘

入场那边已经没有依据可调，于是转向**唯一从未变过的组件**。先确认参数语义：

- `stop_loss_pct: 3.0` 是**价格**的 3%（`stop_distance = price × pct/100`），不是杠杆调整后的
- `size = min(size_by_risk, size_by_alloc)`，而 `size_by_alloc` 恒小于 `size_by_risk`
  （$10 风险预算 / 3% 止损 vs 10% 名义上限）→ **仓位由分配上限决定**
- 二者在 `stop = 10%` 处交叉。所以扫 1.5%~8% 时，**改止损只改离场价位、不改仓位**
  —— 这是个干净的实验
- `safety.hard_stop_pct: 5.0` 有校验：`config.py` 会拒绝 `hard_stop_pct < stop_loss_pct`，
  **报错而非静默截断**（这一点我先猜错了）

同一窗口、三个市场、全量数据集：

| 配置 | 交易 | PF | 策略 | **随机中位** | 超额 | 止损占比 |
|---|---|---|---|---|---|---|
| baseline 3 / 9 | 119 | 1.21 | +4.87% | **+13.40%** | −8.53% | 56% |
| **tight 1.5 / 4.5** | 229 | **1.30** | **+7.55%** | +8.00% | **−0.45%** | 66% |
| wide stop 8 / 9 | 97 | 1.29 | +6.74% | **+16.63%** | −9.89% | 5% |
| no TP 3 / off | 80 | 0.98 | **−0.37%** | +13.27% | −13.64% | 61% |
| wide+noTP 8 / off | 64 | 1.09 | +1.35% | +14.94% | −13.59% | 3% |

**五种配置里，随机方向全都跑赢策略。** 没有一个能让策略超过**它自己的**随机基准 ——
而随机基准用的是同一套离场参数，所以这不是「离场调得不好」，是入场信号的问题。

两个附带观察：

- **收紧离场（1.5/4.5）是唯一把差距压到噪声内（−0.45%）的配置**，而且策略收益从
  +4.87% 升到 +7.55%、PF 从 1.21 升到 1.30。但它同时把随机基准从 +13.40% 压到
  +8.00%，所以改善主要来自「离场变紧」而不是「策略变准」。229 笔 vs 119 笔，
  上涨窗口里暴露度也不同。
- **去掉止盈最差**（策略 −0.37%），而随机仍是 +13.27%。3:1 的止盈结构对策略是有贡献的。

### 顺带抓到一个静默失效的高价值门禁

扫描第一版给出 ETH/SOL 的交易数比 CLI 多 12 笔。追下去发现：**`btc_trend_filter`
在 BTC 数据集缺失时会完全静默失效**。

`btc_trend_direction()` 用 `safe_candles(self.market, "BTC", ...)` 取 BTC ——
**无论交易哪个市场**。而 `safe_candles` 是刻意广泛吞异常的（"a data-layer surprise
must degrade the signal, never take down the trading loop"）。于是 `BacktestMarket`
抛的 `MarketDataError` 被吞掉，过滤器直接跳过：不报错、拦截计数里没有 `macro filter`
行、权益曲线只是长得不一样。

实测（170 天窗口）：

| 市场 | 数据集 | 交易 | macro 拦截 | 收益 |
|---|---|---|---|---|
| ETH | 仅本市场 | 43 | **0** | +2.53% |
| ETH | 含 BTC | 41 | **101** | +1.97% |
| SOL | 仅本市场 | 58 | **0** | **−0.23%** |
| SOL | 含 BTC | 48 | **218** | **+1.88%** |

**SOL 的收益从 −0.23% 翻到 +1.88%，只取决于 BTC 在不在字典里。** 而这是文档记录的
高价值门禁（「该规则本可避开 28 笔亏损中的 14 笔」）。

`run_backtest.py` **是对的** —— 它会为任何市场一并加载 BTC（实测 `--symbol ETH`
输出中有 `loading BTC...`）。所以 CLI 不会踩到。踩到的是**程序化调用方**：
`benchmarks` 模块、扫描脚本、任何手工组装 `datasets` 的地方。

现在引擎在检测到该情形时明确告警，并有测试守住（缺失即告警、存在即安静、
小写键也算已加载）。这是这个代码库第三次出现「门禁静默失效」——
前两次是陈旧窗口和 banner 的假声明。

## 一个比 15m 更要紧的发现：入场信号不如掷硬币

15m 跑完之后顺手核对随机入场基准的**绝对值**（之前只看过百分位列），
结果比 15m 的问题严重得多。同一窗口、同一配置，三个市场全部如此：

| | 策略 | 随机方向（中位） | 随机最差 5% | **买入持有** |
|---|---|---|---|---|
| BTC | +1.02% | +4.51% | **+3.41%** | **+14.61%** |
| ETH | +1.97% | +5.61% | **+3.87%** | **+20.85%** |
| SOL | +1.88% | +3.51% | +1.75% | **+19.00%** |

**策略 < 随机 < 买入持有。** BTC 和 ETH 上，策略连随机的**最差 5%** 都没到；
SOL 上策略刚过 p5，但仍在 p50 之下。

BTC 上 20 次随机方向里 **0 次跑输策略**，而且随机分布的**最低值 +3.02%**
比策略高 2 个百分点 —— 策略不是「略低于随机」，而是落在整个随机分布之外。

对比是**同类的** —— 随机基准复用了同一套门禁、仓位、离场、手续费和资金费，
只把方向换成掷硬币，成交数也只多 33%（40 vs 30）。所以这不是「随机版交易得多
所以赚得多」。

### 拆开看

| | 策略 | 随机 ×20 |
|---|---|---|
| 方向 | 多 16 / 空 14 | 多 384 / 空 409 |
| 多 / 空 盈亏 | +$10.59 / −$0.37 | +$624 / +$239（20 次累计） |
| 离场：**止损** | **13 笔（43%）** | 168 笔（21%） |
| 离场：反转 | 11 笔（37%） | 473 笔（60%） |
| 离场：止盈 | 5 笔（17%） | 138 笔（17%） |

两边方向都是均衡的（策略 16/14，随机 384/409），所以**不是方向偏置**。

差别在离场构成：**策略有 43% 的交易被止损打掉，随机只有 21%**。同一套
3% 止损，策略被打到的比例是随机的两倍 —— 说明策略选的入场点更容易立刻反向。

### 这条结论和前面几条一致

- 鲸鱼因子：PF 在两段之间从 2.00 翻到 0.83，样本外不如不用
- 15m：没有改善，且不产生更多样本
- 门禁：只影响 2 笔交易，不可测
- **入场信号：不如掷硬币**

四件事指向同一处：**这套入场信号没有可测的正向信息量。** 而那 40% 权重的
鲸鱼因子要么无效、要么符号不稳，剩下 60% 的技术+市场因子在随机检验上
是负的。

### 顺带修掉一个误导性的报告缺陷

多币种（`--symbols`）路径**只打印百分位，不打印它所参照的分布** —— 我就是
因此一开始把「pctile 0」读成了「略低于随机」，而它实际意思是「20 次随机全部
更好」。单市场路径有这段，池化路径漏了，而池化恰恰是推荐用法。

现在两个路径都会打印每个市场的随机分布和买入持有。

### 一个必须说明的保留

随机基准的**反转**离场（60%）高于策略（37%），因为引擎允许反转绕开每日上限
和冷却期（这是刻意复刻实盘的行为）。所以随机基准的交易节奏和策略不完全同构
—— 它是「同一套机器、不同的取样」而不是完美对照。

但结论方向不受影响：20 次里 0 次跑输，不是边缘差异。

## 15m 的实测结果：交易数没涨，表现更差

归档接上之后，那个一直没法回答的问题终于可以测了。同一窗口
（`--as-of 2026-09-15`，170 天 × 3 币种），只改入场周期：

```bash
python run_backtest.py --days 170 --symbols BTC,ETH,SOL \
    --as-of 2026-09-15 --candles-archive --entry-timeframe 15m
```

| | 1h | 15m |
|---|---|---|
| bar 数 | 4,801 | **19,201**（4.0 倍） |
| BTC | 30 笔, +1.02%, PF 1.22 | 33 笔, **+2.29%**, PF **1.46** |
| ETH | 41 笔, +1.97%, PF 1.24 | 43 笔, **+0.08%**, PF **1.01** |
| SOL | 48 笔, +1.88%, PF 1.19 | 47 笔, **+0.19%**, PF **1.02** |
| **池化** | **119 笔, PF 1.21, +$48.72** | **123 笔, PF 1.11, +$25.66** |
| 随机入场百分位 | 0 / 0 / 10 | **0 / 0 / 0** |

**bar 数翻 4 倍，交易数只从 119 变到 123（+3%）。**

### 为什么没涨 —— 计数器给的答案

原本的担心是 README 记录的那条：`>400 笔 → 全部亏损`，而 15m 的信号频率是
1h 的 4 倍。先说结论：**交易数没有涨**，但**我原本给的原因（门禁上限）是错的**。
引擎的拦截计数器说明了真实机制：

| | 1h | 15m |
|---|---|---|
| `signals_seen` | 4,080 | **16,320** |
| 每 bar 触发率 | **0.8498** | **0.8500** |
| 被 `threshold` 拦截 | 3,035（74.4%） | **14,440（88.5%）** |
| 被 `already holding` 拦截 | 881 | 1,373 |
| 实际成交 | 30 | 33 |

**原始信号严格按 4 倍缩放** —— 每 bar 的触发率恒定为 0.85，所以 15m 上「出现了
机会」的次数确实是 4 倍。但 **threshold 拦截率从 74% 升到 88%**，多出来的信号
几乎全部没过分数阈值。两个效应抵消，成交数持平。

而且拦截明细里**没有 `daily cap` 这一项**：`max_signals_per_day: 3` 从未触发
（实际只有 0.19 笔/天/币种，离上限差一个数量级）。所以「频率上限挡住了爆炸」
这个说法是错的 —— 结果对，机制不对。

至于 threshold 为什么在 15m 上拦得更多：ADX 和 Supertrend 距离在短周期上系统性
偏小，混合分数因此更容易低于阈值。这是从计数器推断的机制，**没有单独验证**。

### 怎么读这个结果

**两个周期都没有跑赢随机入场**（1h 是 0/0/10，15m 是 0/0/0），所以这轮的结论
是「换到 15m 没有带来改善」，而不是「15m 被证明更差」——123 笔与 119 笔的
PF 差异在噪声范围内。

但有一点是结构性的、不受样本量影响的：**更细的 bar 不等于更多的交易**，
因为阈值把增量吃掉了。所以「换到 15m 能拿到更多样本」这个预期不成立 ——
而这个预期本来是想解决的正是「样本太少、结论测不出来」。

BTC 在 15m 上明显更好（PF 1.22 → 1.46），ETH 和 SOL 掉到盈亏平衡。
这个分化在 33-47 笔的样本上同样是噪声，不足以支撑「15m 只适合 BTC」。

## 接上 candles 归档：窗口不再受 API 限制

回测的窗口一直卡在**公开 API 的 5000 根上限**上：

| 周期 | API（5000 根） | 归档（414 天） |
|---|---|---|
| 1h | 208 天 | **414 天** |
| 15m | **52 天** | **414 天** |
| 4h | 833 天 | 414 天 |

后果是两件事做不了：**15m 之类的高频周期无法验证**（52 天不够任何结论），
以及**第二段独立窗口不存在**（170 天交易 + 30 天预热已经把 200 天用尽）——
上一节那个「两段不重叠」，拆出来的是总历史里仅有的两段。

```bash
python run_backtest.py --days 276 --as-of 2026-09-17 --candles-archive
```

归档存的是**秒级** bar（日分区、260 个币种），任意周期都由它重采样得到。

### 重采样是精确重建，不是近似

```sql
epoch_ms(time_bucket(INTERVAL '1 hour', timestamp)) AS t,
arg_min(open,  timestamp) AS o,   -- 首笔的开盘价
max(high)                 AS h,
min(low)                  AS l,
arg_max(close, timestamp) AS c,   -- 末笔的收盘价
SUM(volume)               AS v
```

`arg_min`/`arg_max` 取的是**首末笔**，这正是交易所自己做 bar 的方式，所以重建
是精确的。校验：拿 API 自己返回的 1h bar 逐根对比，**8 个样本横跨 7 个月，
OHLC 与成交量偏差全部为 0**。

更强的校验是端到端等价 —— 同一窗口（`--as-of 2026-09-15`, 170 天）跑两次：

| | API 路径 | **归档路径** |
|---|---|---|
| BTC | 30 笔, +1.02%, PF 1.22, pctile 0 | **完全相同** |
| ETH | 41 笔, +1.97%, PF 1.24, 0 | **完全相同** |
| SOL | 48 笔, +1.88%, PF 1.19, 10 | **完全相同** |
| 池化 | 119 笔, 34.5%, $+0.41, PF 1.21, +$48.72 | **完全相同** |

**每个数字都相同**，所以归档是真正的即插即用替换。归档路径用独立的缓存键
（`arc_candles_`）：两者本应一致，若哪天不一致，共用键会把它藏起来而不是暴露。

### 踩到的一个坑（写下来因为它长得不像 bug）

第一版校验给出 `o=64185` 而 API 是 `o=65494`，量比 18.6 倍 —— 看起来像数据错了。
实际是我的**查询有 timezone bug**：列是 `TIMESTAMPTZ`，而我拿 `epoch_ms(...)`
（返回裸 `TIMESTAMP`）去比较，隐式转换走会话时区，**窗口整体偏移了 8 小时**
（机器是 UTC+8）。它给出的是**真实但错误时段**的 bar，不会报错。

实现里因此固定用 `to_timestamp()`，并有一条测试专门守这一点——
在 UTC / Asia-Shanghai / America-New_York 三种时区下输出逐位相同。

### 一个必须说清的缺口

**归档没有 funding。** 它含 positions / fills / candles，不含资金费历史，
所以接了归档之后 candles 来自本地、**funding 仍走 API**。实测 API 的资金费
能回溯到与归档相当的范围（300 天窗口覆盖 100%），但覆盖不足时加载器会明确
告警「未覆盖的日子按零资金费计费」——那会**美化多头的持仓成本**。

### 对鲸鱼因子问题的实际影响：比预期小

归档有 414 天，但**鲸鱼问题受 positions 的 52 天缺口限制**：

| 数据集 | 覆盖 | 缺口 |
|---|---|---|
| candles | 414 天 | — |
| fills | 417 天 | — |
| positions | 364 天 | **2025-10-25 → 12-15** |

于是可用区块只有：

* **B：2025-12-15 → 2026-09-17（约 277 天）** —— 可用于鲸鱼测试
* A：2025-08-01 → 2025-10-24（约 85 天）—— **不可用**，因为选钱包需要窗口
  之前的历史，而 positions 从 2025-07-29 才开始，前置不足 91 天

**277 天 vs API 的 200 天，只多了 1.4 倍。** 归档对这个问题的帮助有限 ——
它真正解锁的是 **15m**（52 天 → 400 天）。

## 聪明钱因子的首次回测（近似版）

那 40% 的权重此前从未被回测过 —— 公开 API 没有历史持仓，因子在回测里
被整个禁用，对齐门禁也被迫关闭。现在它跑起来了：

```bash
python run_backtest.py --days 170 --symbols BTC,ETH,SOL --whale-snapshots
```

### 结果：权重与门禁必须分开测，而且结论随时间翻转

**这一节的第一版是错的，先说清楚错在哪。** 第一版用 `--days 170` 对比了
「含鲸鱼 / 不含鲸鱼」，得出「PF 持平在 1.21、总盈亏更低」。但 `--days` 是锚在
**运行时刻**的，两次运行描述的其实是不同的时间段 —— 那个结论里混进了窗口漂移。

现在用 `--as-of 2026-09-15` 钉住窗口（两组都是 `2026-02-27 -> 2026-09-15`，
4801 根 1h bar），并把**权重**和**门禁**分开测：

| 组 | 鲸鱼权重 | 对齐门禁 | 交易 | PF | 期望/笔 | 总盈亏 |
|---|---|---|---|---|---|---|
| A | 因子禁用 | 关 | 119 | 1.21 | $+0.41 | +$48.72 |
| B | **0.40** | **关** | 69 | **1.43** | $+0.85 | **+$58.58** |
| C | 0.40 | **开** | 67 | 1.36 | $+0.72 | +$48.33 |

B 组由 A/C 的配置改**一行**得到（`discipline.require_smart_money_alignment: false`）后运行
`--config` 得到。这里刻意不留一份配置副本：整份复制的配置会在主配置演进时**静默漂移**，
让「B 组」实际上跑的是别的东西。

钉住窗口后，**鲸鱼权重看起来是帮忙的**（1.21 → 1.43），和第一版结论相反。

**但门禁那一组不成立：** B 与 C 的 ETH 和 SOL **逐字相同**（25 笔 PF 1.33 /
27 笔 PF 1.18），门禁只影响了 BTC 的 **2 笔**交易。「门禁拖累策略」建立在 2 笔
样本上，不可测。

### 关键检验：把 170 天拆成两段不重叠的窗口

API 只有 200 天历史（170 + 30 预热已用尽），但可以拆成两段**交易日不重叠**的
区间，这才是判断「1.21 → 1.43 是真效应还是噪声」的办法：

| 段 | 组 | 交易 | PF | 总盈亏 |
|---|---|---|---|---|
| H1 (3/29–6/15) | A 无鲸鱼 | 57 | 1.43 | +$43.20 |
| H1 | **B 有鲸鱼** | 37 | **2.00** | **+$63.41** |
| H2 (6/16–9/15) | A 无鲸鱼 | 65 | 1.09 | +$12.09 |
| H2 | **B 有鲸鱼** | 33 | **0.83** | **−$12.04** |

**鲸鱼因子在两段之间翻转了符号：PF 2.00 → 0.83。** 全窗口那个「1.21 → 1.43」
完全由 H1 贡献；在 H2 里它**亏钱**（−$12.04，而不用它 +$12.09）。

这和上一轮的 walk-forward 结论一致（那条记录在 `bots/fox_btc.yaml` 的注释里）：

```
             no filter   ceiling=10   no whale data at all
in-sample      1.30        1.32            -
out-of-sample  0.43        0.79           1.02
```

两条独立证据都指向同一件事：**这个因子的效果在不同时段之间不稳定，样本外
不如完全不用它。**

### 样本量才是真正的瓶颈

四组 × 三个市场 = **12 次随机入场检验**。纯随机情况下，超过 75 百分位的期望值
是 **3 个**，至少出现 1 个的概率是 **96.8%**。实际观测到 **1 个**（H1-B 的
BTC）—— **比随机还少**。

所以正确的读法是：**没有任何一组，包括当前线上配置，在随机入场检验上取得
了可复现的优势。** 单看某一组的 PF 高低没有意义 —— 每次对比只有 33–119 笔交易，
而随机入场的分散度本来就覆盖这个区间。

### 两个静默 bug（都已修）

**1. 陈旧窗口用错了量级。** `HistoricalSmartMoney` 的 `max_age_ms` 默认 **6 小时**，
那是为**小时级资金费**数据定的。而归档快照是**日级**的 —— 6 小时窗口下，
日快照几乎永远陈旧。实测：

| 陈旧窗口 | 48 根 bar 中有持仓的 |
|---|---|
| 6h（引擎默认） | **12** |
| 26h（日级需要） | **48** |

**因子此前有四分之三的时间是「盲」的，而且不报错** —— 它只是报告「没有持仓」，
读数看起来完全正常。

**2. 警告说了不成立的话。** 引擎无条件地声明
「per-wallet unrealised PnL cannot be reconstructed, so the wallet-quality
confidence term is excluded」。这对资金费路径成立，对快照路径**不成立** ——
快照带 `entry_price`，质量项是**启用**的：

```
pnl_available      True
in_profit_pct      58.0      <- 真实计算，不是猜的中点
```

现在警告按实际数据分三种情形（全部有 / 部分有 / 全无）分别陈述。

### 一个副产品：质量项第一次用上真实值

资金费路径没有开仓价，`pnl_available=False`，打分器只能用区间中点 0.75 代替
真实的 `winner_ratio`。快照有开仓价，所以这一项第一次是**算出来的**：

```python
quality_conf = 0.5 + 0.5 * winner_ratio     # 真实值
```

顺带修正了口径：名义值按**当前 bar 的价**标记，而不是快照自带的（那是快照时刻的，
最多滞后一天）。开仓价是不变的历史事实，值得保留；快照的名义值不值得。

### 必须说清的三个限制

**1. 钱包集不是排行榜。** 实盘按**盈利能力**选钱包，重建那个需要 `fills`。
本版用**规模 + 持续性**近似（150 / 4,253，3.5%），这是不同的东西 ——
**持仓大不等于判断对**。

**2. 选钱包只用窗口之前的数据。** 用窗口本身会选出「在这段里活下来的」，
而那正是回测要测量的答案。

**3. 日级 vs 15 分钟。** 实盘每 15 分钟刷新，回测每天只能更新一次。

再加上归档在 2025-10-25 ~ 12-14 有 51 天缺口（源侧），窗口跨越那段时持仓读为空。

### 补齐了：用 `fills` 重建排行榜（生产规则）

近似版的软肋是「按规模选钱包 ≠ 按盈利能力选」。`fills` 归档（417 天、
13.91 GB、$0）让真正的规则可以复现：

```bash
python run_backtest.py --days 170 --symbols BTC,ETH,SOL \
    --whale-snapshots --whale-leaderboard
```

`backtest/leaderboard.py` 逐日复现生产的选择逻辑 —— 按 `day`/`week`/`month`
三个窗口的**已实现盈亏**排名，各取前 60 并集，按跨窗口命中数封顶 150。钱包集
**逐日变化**：一个钱包只在它当期在榜的那些天贡献仓位点，掉出榜单即停止被参考。

### 三方对比（同口径，170 天 × 3 币种）

| | 无鲸鱼（基线） | 规模近似 | **排行榜（生产规则）** |
|---|---|---|---|
| 池化交易 | **117** | 67 | 102 |
| 胜率 | **33.3%** | 31.3% | **28.4%** |
| profit factor | **1.21** | 1.21 | **1.03** |
| 总盈亏 | **+$48.68** | +$29.51 | **+$6.74** |
| 随机入场百分位 | 0 / 0 / 5 | 0 / 0 / 0 | 0 / 0 / 0 |

**生产的选择规则表现最差。** 它不是「没用」，而是**主动有害** ——
profit factor 从 1.21 掉到 1.03，胜率从 33.3% 掉到 28.4%，
总盈亏从 +$48.68 掉到 +$6.74。

这比近似版的结论更强：近似版只是「没有改善」，而**按盈利能力选钱包
这个规则本身，在这段样本上是负贡献的**。

一个可能的解释值得记下来：按 PnL 排名会系统性地选中**做市商和高频账户**
（单日数千笔成交，靠提供流动性赚钱），而它们的持仓方向**不代表方向性观点**。
把它们的仓位当成「聪明钱的方向判断」来读，是在读取一个不存在的信号。

### 追查：是因子无效，还是选错了钱包？

「排行榜最差」有两种解释 —— 因子本身无效，或者**选钱包的规则选错了人**。
后者是可检验的，于是去量了一下入选钱包的成交频率：

| 成交频率 | 入选占比 | 中位月盈亏 |
|---|---|---|
| <10 笔/天（方向性交易者） | **0.4%** | $540k |
| 10-50 | 3.4% | $863k |
| 50-200 | 10.1% | $952k |
| 200-1000 | 32.7% | $1.15M |
| **>1000 笔/天（做市商）** | **53.4%** | **$1.89M** |

中位盈亏随成交频率**单调递增** —— 按**绝对 PnL** 排名，实质上是在选
**最活跃的账户**。前 60 名里 **86% 是高频账户**，而真正的方向性交易者
（<10 笔/天）只占 **0.4%**。

做市商的持仓是**库存**，不是方向性观点。把库存当信号读，读的是不存在的东西。

于是加一个成交频率上限再排名（`--whale-max-fills-per-day`）：

| 频率上限 | PF | 胜率 | 总盈亏 | 随机入场百分位 |
|---|---|---|---|---|
| **无（= 生产规则）** | **1.03** | 28.4% | +$6.74 | 0 / 0 / 0 |
| <200 笔/天 | 1.38 | 38.4% | +$76.76 | 0 / 60 / 0 |
| **<50 笔/天** | **1.52** | 38.1% | **+$95.41** | 0 / 0 / 15 |
| <10 笔/天 | 1.47 | 37.2% | +$89.74 | 0 / 5 / 20 |

**驼峰形，峰值在约 50 笔/天。** 400 天的样本、三个币种，PF 从 1.03 升到 1.52，
总盈亏从 +$6.74 升到 +$95.41（基线的 2 倍）。

### 结论修正

之前那版结论「生产的选择规则是负贡献的」**不够准确**。准确的说法是：

**因子本身是有效的（PF 1.52 > 基线 1.21），但生产用纯 PnL 排名选钱包，
系统性地选中了做市商，把信号淹没了。**

这不是「因子无效」，而是**一个可以修的实现缺陷**：给排行榜加一个活跃度上限。
生产配置里目前没有这个约束。

需要注意这只是一种解释，且证据强度有限 —— 三个币种仍无一突破随机入场的
第 75 百分位，112 笔样本也不算大。但**单调的剂量-反应关系**（1.03 → 1.38 →
1.52）比单点结果更难用噪声解释。

### 误差棒：点估计还不够

上面那些 PF 都是点估计。112 笔样本能不能把它们区分开？对逐笔 `net_pnl`
做引导法重采样（20,000 次）后：

| | 无鲸鱼（基线） | 排行榜 + 上限 50 |
|---|---|---|
| 交易数 | 119 | 112 |
| PF | 1.24 | **1.54** |
| **PF 的 95% 置信区间** | **[0.80, 1.82]** | **[0.98, 2.31]** |
| 总盈亏 | +54.08 | +98.66 |
| **总盈亏 95% 区间** | **[−50.95, +164.92]** | **[−3.80, +203.11]** |
| **P(PF < 1.0)** | 16.7% | **3.0%** |

三个结论：

1. **基线的盈利能力在统计上不成立** —— PF 区间 [0.80, 1.82] 跨过 1.0，
   有 16.7% 的概率真实 PF 低于 1。
2. **最好的配置，区间下沿仍贴着 1.0**（0.98）。改善是**暗示性的，不是已确立的**。
3. 两个区间高度重叠，所以「1.54 优于 1.24」这句话，**样本支撑不了**。

真正稳健的信号是 **P(PF < 1.0) 从 16.7% 降到 3.0%** —— 风险下降比收益上升
更可信，因为它对少数几笔极端交易的依赖更小。

教训：`PF 1.52` 和 `PF 1.03` 摆在一起很有说服力，但**两者都落在同一个噪声带里**。
在拿到更多样本之前，不该基于这个差值做更大的投入。

### 样本外验证：那个结论不成立

`50 笔/天` 是我在**同一个窗口**上看 10/50/200 选出来的。这是样本内选择 ——
胜出的那个值，有一部分只是在拟合那段时期的噪声，所以它的 PF 天然偏高。

把可用的 1h 历史（208 天，恰好撞在 API 的 5000 根上限上）切成两半：
**前 104 天调参，后 104 天只评估一次**，且调参时不允许看后半。窗口用 `--as-of` 钉死。

| 窗口 | 配置 | 交易数 | PF | 胜率 | 总盈亏 |
|---|---|---|---|---|---|
| **前半年**（调参） | 无过滤（生产规则） | 68 | 1.30 | 33.8% | +40.55 |
| | ceiling=10 | 72 | **1.32** | 36.1% | +41.00 |
| | ceiling=50 | 69 | 1.30 | 34.8% | +35.77 |
| | ceiling=200 | 73 | 0.71 | 27.4% | −43.49 |
| **后半年**（评估） | **完全不用鲸鱼** | 70 | **1.02** | 28.6% | **+3.07** |
| | ceiling=10（前半选出） | 72 | 0.79 | 25.0% | −30.08 |
| | 无过滤（生产规则） | 64 | **0.43** | 17.2% | **−86.23** |

**三条结论，每一条都推翻了前面写的东西：**

**1. 「PF 1.03 → 1.52」是样本内产物。** 在前半段，这一对是 **1.30 → 1.30**；
在后半段，过滤版是 **0.79**。之前那个漂亮的对比，窗口恰好覆盖了用于选参的那段。

**2. 「单调剂量-反应」也是噪声。** 我之前把 `1.03 → 1.38 → 1.52` 的单调性称为
「强证据」。在前半段，`ceiling=200` 的 PF 是 **0.71**（之前测出 1.38），
方向和之前相反。

**3. 因子本身的价值没有确立，而且方向在两半之间翻转。**
前半年：有因子（1.30/1.32）≈ 无因子；后半年：**不用因子最好**（1.02），
用因子反而更差（0.43 / 0.79）。

**那活跃度上限还有没有依据？** 有一点，但比之前说的弱得多：
它在前半段边际改善（1.30 → 1.32）、在后半段改善明显（0.43 → 0.79），
**两半方向一致** —— 这是唯一的稳健信号。但即便如此，
过滤后的因子（0.79）**仍然不如根本不用它**（1.02）。

所以真正的开放问题不是「该不该加活跃度上限」，而是
**这 40% 的权重本身是否站得住**。配置里保留了 `max_fills_per_day: 50`
（它是两种因子配置里较好的那个），但注释已改成「不是因为它被证明有效」。

### 这轮暴露的方法论问题

窗口锚定当前时间 → 同一条命令隔几小时跑就是不同时期。这一轮把它修了
（`--as-of`），但**修好之后才发现，之前所有跨窗口的比较都是在流沙上做的**。
固定窗口的第一次运行就精确复现了最早那次（14 笔 / +1.24%），
确认了之前看到的差异纯粹来自窗口漂移。

### 落到生产配置：活跃度上限

回测的结论只有落到能跑的代码上才有意义。`smart_money.max_fills_per_day`
已加入配置，默认 **50**：

```yaml
max_fills_per_day: 50   # null 则关闭，完全恢复原行为
```

实现上有三点比过滤器本身更重要：

- **取数失败就保留该钱包。** 丢弃会让网络抖动清空钱包集，而空集会被对齐门禁
  拦下**每一笔**交易。fail-open 退化成今天的行为，而不是退化成停摆。
- **白名单钱包不参与测量。** 这个上限是筛做市商的，不该否决手工验证过的钱包。
- **全部被剔除时拒绝返回空集**，与已有的 `min_persistence` 回退规则一致。

`userFills` 最多返回 2000 条最近的成交，**而这个上限本身就是判据**：高频账户
返回满 2000 条且跨度只有几小时，低频账户返回全部且跨度为几个月。一次请求即可判定。

### 但它在实盘上的作用范围比回测里小得多

真实 API 冒烟测试（同一个排行榜，只差上限）：

```
无上限: 13 个钱包
上限50: 12 个钱包   (剔除 1 个, 额外耗时 22s)
  activity ceiling 50 fills/day dropped 1 high-frequency wallet(s);
  11 unmeasurable and kept
```

**12 个候选里 11 个无法测量。** 追查原因时发现了一个更基础的问题：

```
排行榜前三名（月盈亏 $277M / $222M / $119M）
  账户价值:  $1.15B / $2.46B / $912M      <- 排行榜口径
  clearinghouseState accountValue: 0 / 4500 / 9500,  持仓数 0
  userFills: 0 条
```

**这些账户在主 perp dex 上什么都没有** —— 它们的高盈亏和「账户价值」来自其他
dex 或现货。这有两个后果：

1. 它们本来也贡献不了任何仓位（因子读 `clearinghouseState`，拿到空）
2. 活跃度过滤器对它们无法测量，因此保留

所以过滤器的实际作用范围是**真正在主 dex 交易的账户**，恰好也就是能贡献仓位的
那批。这不是没用，但**不能假定它会复现回测里 1.03 → 1.52 的改善** —— 回测是在
用 `fills` 重建的排行榜上做的，那里每个钱包按构造都有成交记录。

**结论：这个上限已实现、已测试、可配置，但它需要先在实盘观察一段时间
再决定是否信任。** 默认值 50 来自回测，而回测的数据路径与实盘不同。

### 顺着这条线做的下一步：按「真实账户价值」过滤

排行榜前几名在主 dex 上没有仓位，提示了一个独立的改法：用 `clearinghouseState`
的真实账户价值过滤，而不是排行榜自报的那个。已实现为
`smart_money.min_live_account_value`（默认 10000）。

实测规模：三个窗口的并集里 77 个钱包通过 `min_account_value`，其中 **59 个（77%）
的主 dex 账户价值恰好为 0**，而它们在排行榜上标着几亿到几十亿 —— 那个数字覆盖
账户触及的**所有**场所，与 agent 实际交易的 dex 无关。

**但效果和我预期的不一样，我在中途纠正了自己：**

```
无 floor: 77 个钱包 -> 实际产出 6 个 BTC 仓位
有 floor: 18 个钱包 -> 实际产出 6 个 BTC 仓位     <- 完全相同
```

我原本断言「`max_wallets` 上限会裁掉活跃账户，所以过滤能腾出槽位」。**实测不成立**
—— 并集只有 77，上限 150 从不触顶，没有任何活跃账户被裁掉。

而更早我还报过一个「并集 180、62% 是空账户」的数字，**那个测量本身就是错的**：
我复现时 `taken` 只计新地址，实盘代码计所有行，所以我把并集算大了 2.3 倍。

修正后的结论：**这是一个卫生与效率修复**（每次快照从 77 次钱包读取降到 18 次），
**不是信号改善**。它让 `wallets_selected` 描述真正存在于本场所的账户。

### 这轮修掉的 6 个缺陷

审查阶段发现的，每个都有测试覆盖（变异验证 5/5 捕获）：

| 缺陷 | 后果 |
|---|---|
| tiebreak 排序方向写反（`DESC`） | 上限触顶时**优先保留名次最差**的钱包 |
| 覆盖度按全局跨度而非窗口重叠计算 | 警告**从不触发**，69/169 天被当成全覆盖 |
| 并行序列逐个 append（转换失败会错位） | `points`/`entries` 长度不一致 |
| SQL 用 `-c` 传参 | 钱包数超 3,214 时触发 `ARG_MAX`（单参数 128KB 上限） |
| 缓存签名只看文件清单不看内容 | 重抓某天后**误用陈旧排名** |
| 引擎硬编码「按规模选择」的警告 | 排行榜路径下**说了不成立的话** |

## 指标审计：现有指标与是否需要新增

### 现有指标的实际接入情况

`agent/indicators.py` 实现了 6 个指标，但**真正进入决策的只有 4 个**：

| 指标 | 在策略中的角色 | 调用点 |
|---|---|---|
| Supertrend | 入场周期方向 + 离轨距离（权重 0.40）；高周期门禁 | 3 |
| EMA | 快/慢线间距（0.25） | 2 |
| RSI | 动量（0.20） | 1 |
| ADX | 趋势强度 —— **不进打分，只调置信度** | 1 |
| ATR | 止损距离与头寸规模（唯一用于风控的指标） | 1 |
| SMA | 库工具函数，未被策略调用（README 中作为库能力列出） | 0 |

非技术类输入：资金费率（拥挤度，反向）+ 24h 涨跌（动量）。

### 结论：现在不该加指标

**1. 现有信号本身没有可证明的优势。** 把样本从 14 笔扩到 118 笔之后：

| | BTC | ETH | SOL | 池化 |
|---|---|---|---|---|
| 交易笔数 | 30 | 41 | 47 | **118** |
| 胜率 | 40.0% | 31.7% | 29.8% | 33.1% |
| profit factor | 1.20 | 1.22 | 1.18 | 1.20 |
| 收益 | +0.93% | +1.79% | +1.84% | |
| buy & hold | +11.77% | +15.41% | +21.04% | |
| 随机入场百分位 | **0** | **0** | **10** | 无市场超过 75 |

三个币种**全部**无法胜过随机入场，且大幅跑输 buy & hold。

**2. 40% 的权重无法回测。** 公开 API 无历史鲸鱼持仓，聪明钱因子无法回放，
回测中该门禁被迫关闭 —— 也就是说回测跑的**不是**部署的策略。

**3. 与项目自身结论相反。** README 引言记录：`>400 笔 → 全部亏损`、
`纯 TA −18%`。指标越多 → 信号越多 → 交易越多 → 正是那个失败模式。

在 118 笔样本下试 N 个指标，**必然**能找到「赢家」，但那全是噪声。

### 附带修正：两处「文档与实现不一致」

**持仓量被设计但未实现。** `market_factor.py` 的 docstring 原本声称结合
crowding（资金费率）与 regime（持仓量）两种读法，但 `oi_growth` 算出来之后
**只被拼进日志字符串**，从未进入 `score` 或 `confidence`。

现在文档如实描述，持仓量增长写入 `details["oi_growth_pct"]`，
并**明确写出它不进打分的原因**（假说未经评估，且无历史数据可回测）。

**持仓量增长在生产中恒为 0。** `_prev_oi` 是**进程内**字典，而定时任务是
`run_bot.py --cycles 1` —— 每 15 分钟一个全新进程。实测 27 条记录中只有 1 条
非零（来自手工跑的两周期）。该字段的含义是「没有上一次读数」，
而非「没有变化」。**离线评估应改用连续的 `open_interest_usd` / `open_interest_base`。**

### 测量能力：新增 `--symbols`

单币种 90 天只有 14 笔，指标模块自身就会警告「低于 30 笔没有统计意义」。
新增 `--symbols` 一次跑多市场并输出池化样本：

```bash
python run_backtest.py --days 170 --symbols BTC,ETH,SOL
```

单币种路径的输出保持**逐字不变**。`--symbol` 与 `--symbols` 同时给出会显式报错，
而不是静默选一个 —— 否则敲错的命令会跑出看似可信的错误结果。

### OI 假说能否离线验证

结论：**当前不能，且回测永远不能。**

- 公开 API 只有 `metaAndAssetCtxs`（仅当前值），没有历史持仓量接口
- `backtest/market.py` 因此硬编码 `open_interest=0.0`
- 唯一路径是向前积累实盘 journal 数据

所需数据已经在记录中（`open_interest_base` + `open_interest_usd`）。

**一个必须注意的混淆**：`open_interest_usd = 持仓量 × 价格`，所以它的增长
**混入了价格变动**。例如价格上涨 5% 而仓位不变，名义持仓量也会涨 5%。
要检验「新杠杆资金进场」，应使用 **`open_interest_base`**（币数量），
它才是纯粹的仓位变化。

## 测试套件审计：哪些测试真正承重

测试数量本身不是指标 —— **测不出问题的测试等于零**。用变异测试实测：
故意破坏 9 处生产行为，看哪些测试会失败。

### 第一次结果：2 个变异存活

| 变异 | 捕获 |
|---|---|
| 回测止损忽略跳空 | ✅ 1 个测试 |
| 挂单 oid 不再被记录 | ✅ 2 个测试 |
| 非有限浮点不再被拒绝 | ✅ 4 个测试 |
| **固定临时文件名（并发）** | ❌ **0 —— 存活** |
| 平仓失败仍报成功 | ✅ 1 个测试 |
| **持仓方向符号丢失** | ❌ **0 —— 存活** |
| 冷却期永不生效 | ✅ 2 个测试 |
| 置信度丢掉盈利占比 | ✅ 2 个测试 |

### 存活 1：我自己上一轮加的并发测试是废的

它的断言是「没有异常逃逸」+「文件仍可解析」。但 `save()` 会把
`os.replace` 的失败**吞成 `False`**（`except OSError: return False`），
所以固定临时文件名导致的写入失败**根本不会抛异常** —— 测试无论如何都通过。

修复：断言**每个写入者都返回 True**。这才是能区分两种实现的断言。

### 存活 2：仓位方向的符号约定完全没有测试

`size` 承载方向，`notional` 必须与它同号。而消费方**显式取负**：

```python
239:        return sum(-p.notional for p in self.shorts)
```

符号一旦丢失，`short_notional` 由 +60 变成 **−60**，
`long_ratio_pct` 从 62.5% 变成 **250%** —— 因子会把一个**重度做空**的市场
读成**多头共识**。这是打分链路的主输入，却没有任何测试保护。

**根因**：测试全部用 `WalletPosition(...)` **直接构造**一致的数据，
从未执行产生符号的**解析代码**。而该约定在两处被逐字重复
（`abs(notional) if size > 0 else -abs(notional)` × 2），
散落意味着没有单一可测的锚点。

修复：提取 `signed_notional(notional, size)`，约定只说一次；
新增 `TestNotionalSignConvention`，既测辅助函数，也**驱动真实解析器**
（stub 掉 `request_json`）验证交易所载荷中的无符号 notional 被正确赋予符号。

### 第二次结果：9/9 全部捕获

| 变异 | 捕获（修复后） |
|---|---|
| 固定临时文件名 | ✅ 1（且实测稳定：正确代码 20/20 通过，变异代码 10/10 捕获） |
| `signed_notional` 函数体去符号 | ✅ 3 |
| 调用方绕过 `signed_notional` | ✅ 1 |
| 其余 6 项 | ✅ 均保持捕获 |

### 关于「327 个是否都需要」

实测数据：**62 个类、平均 5.3 个用例**，无上帝类；**无断言的测试 0 个**、
**完全重复的测试体 0 组**；全套 **4.2 秒**跑完（其中回测占 3.3 秒）。
随机抽查最大的 `TestLeaderboardParsing`（16 个），覆盖的是
「解析嵌套载荷 + 多窗口并集 + 持续性加权 + 排序」四个不同行为，不是凑数。

结论：**没有需要删的测试，但有 2 个需要修的** —— 一个测不出问题（已修），
一个本该存在却缺失（已补）。数量不是问题，**能不能失败才是**。

## 第四轮审查：崩溃恢复路径（`agent/state.py`）

这是全项目唯一只被间接覆盖的关键防线 —— 它决定「进程被杀死后能否正确恢复」。
先说**验证为正确的部分**，再说问题。

### 审查确认无问题的部分

- **启动对账的四种情形齐全**：跟踪空/交易所有 → 采纳；跟踪有/交易所空 → 清除；
  两者都有但不一致 → **采信交易所**并记事件；一致 → 仅记录。对账失败时抛
  `CriticalExecutionError` 拒绝交易，而不是猜测。这是正确且保守的设计。
- **`shutdown()` 刻意不强制平仓** —— docstring 的理由充分：每次重启都变成市价单
  比留一个待恢复的仓位更糟。
- **`peak_equity` 确实随状态持久化**（经 `asdict()`）。

> 最后一条值得记录：我最初怀疑 `_persist()` 漏写了 `peak_equity`（该函数逐字段
> 赋值，确实没有它），差点作为 bug 上报。**实测发现它经 `asdict()` 正常往返** ——
> 因为 `check_drawdown` 直接写在 `self.state` 上，序列化的是整个对象。
> 如果只靠读代码，这会是一次误报。

### 🟡 非有限浮点会静默废掉守卫

`_as_float` 接受 `inf`/`nan`，而它们的**所有比较都为假**：

| 字段被污染为 | 失效的守卫 | 原因 |
|---|---|---|
| `peak_equity = inf` | 回撤熔断 | `(inf - equity)/inf = nan`，`nan >= limit` 为假 |
| `last_trade_ts = nan` | 冷却期 | `(now - nan) < cooldown` 为假 |
| `halted_until = nan` | 连亏熔断 | `now < nan` 为假 |
| `trades_today = nan` | 每日上限 | 计数比较为假 |

危险之处在于**守卫看起来还在，只是永远不触发** —— 没有任何报错。

而且这是**自洽的污染路径**：`json.dumps` 会把 `inf` 写成 `Infinity`
（**非法 JSON**），`_as_float` 又能把它读回来。已实测确认。

修复：新增 `_finite()`，非有限值一律拒绝；`save()` 用 `allow_nan=False`，
宁可写入失败（保留上一个有效文件）也不污染下次启动。

### 🟡 固定临时文件名 → 并发写会互相污染

```python
tmp = self.path.with_name(self.path.name + ".tmp")   # 两个进程共用同一个文件
```

这个项目**明确支持两个进程并存**（cron 每 15 分钟一个周期进程 + 手动运行，
README 里还专门警告过）。两者同时写会交错进同一个临时文件，
再由 `os.replace` 把混合物发布成正式状态 —— 而损坏的状态文件 `load()` 返回
`None`，**一次性重置全部护栏**。

修复：改用 `tempfile.mkstemp()` 为每个写入者分配独立临时文件。
实测 24 个线程并发写入：无异常、无残留临时文件、文件始终可解析。

### 🟢 docstring 承诺超出实现（缺 `fsync`）

原文写「临时文件 + rename 使崩溃不会留下损坏文件」。这对**进程崩溃**成立，
对**断电/硬重启**不成立：rename 可能已持久化而数据还在页缓存里。已补
`flush() + fsync()`，并修正文档措辞。

### 🟢 裸 `assert` 记录不变量

`reconcile_startup` 用 `assert live_pos is not None and ...` 收窄类型。
`-O` 下断言被剥离，后续代码会直接解引用 `None`。虽因前置分支的穷尽性当前无害，
但已改为显式守卫。

### 验证

- **327 个测试通过**（+8），新增覆盖：inf/nan 在各字段被拒绝、
  `save` 拒绝写入非有限值且保留旧文件、落盘文件通过**严格** JSON 校验、
  24 线程并发写不损坏不残留
- 端到端正常，无残留临时文件，零 lint

## 开发中实测发现并修正的陷阱

这些全部是先跑出问题、再定位、再补回归测试，值得记录：

1. **`openInterest` 是币数量，不是美元。** 主网 BTC 返回约 37,400，
   乘以 markPx 约 $77k 得到 $2.9B 才符合常识。最初按美元处理，算出 $0.0M。
   现通过 `AssetContext.open_interest_notional` 转换。

2. **排行榜不在 `/info` 端点。** `{"type":"leaderboard"}` 稳定返回 HTTP 422。
   正确地址是 `https://stats-data.hyperliquid.xyz/Mainnet/leaderboard`，
   返回 `leaderboardRows` + `windowPerformances`。

3. **37MB 响应会导致传输截断。** `http.client.IncompleteRead` 被当作致命错误。
   修复：改用分块读取以便重试，并禁用压缩（`Accept-Encoding: identity`，
   实测压缩正是截断诱因）。另加 256MB 响应上限，防止服务端异常时无限缓冲。

4. **主网钱包 + 测试网 API = 空结果。** 见上方"数据源设计"。

5. **测试桩缺少 EOF 信号会死循环。** 分块读取依赖 `read()` 返回空字节终止；
   一个永远返回数据的测试桩会让测试挂死。已修正测试并加响应体上限作为生产侧防御。

6. **持续性硬过滤会降低信号覆盖。** 见「聪明钱因子的选钱包逻辑」——
   把持续性从筛选条件改成权重，是这一轮改进里最反直觉但也最关键的结论。

7. **重启会清空所有护栏。** 当日次数、冷却、连亏熔断、持仓都只在内存里。
   已做持久化（见「护栏跨重启」）。

8. **`restore_payload` 只接受 dict，传对象会静默重置。** 传入 `AgentState`
   对象时 `data.get()` 抛 `AttributeError`，被兜底逻辑吞掉并返回全新状态 ——
   等于护栏又白存了。现在兼容 dict 与对象两种形态，并有专门的回归测试。

9. **配置在说谎。** `max_drawdown_pct` 和 `reduce_only_on_exit` 从未被任何代码引用。
   前者已实现，后者已删除并在文档里说明原因（退出走 `market_close`，
   本身就是 reduce-only，该开关只能是装饰）。

10. **未成交的挂单被当成成交。** 见「资金安全机制」第 2 条。

## 定时采集（cron）

公开 API **没有历史鲸鱼持仓接口**，所以「聪明钱因子能否回测」这件事完全取决于
从现在起积累多少历史。`scripts/collect.sh` 承担这件事，已注册为每 15 分钟一次的
cron 任务。

### 它做两件事

| 步骤 | 产物 | 用途 |
|---|---|---|
| `record_snapshots.py --symbols BTC,ETH` | `snapshots/whale_positions.jsonl` | 每个钱包的持仓 + 选币元数据，是日后回测 40% 因子的唯一数据源 |
| `run_bot.py --cycles 1` | `logs/journal.jsonl` | 一轮 dry-run 的信号、三因子明细、门禁拒绝原因、模拟订单 |

每次调用都是**新进程**，但会从 `logs/agent_state.json` 恢复持仓状态，所以累积下来的
journal 读起来是一段连续会话，而不是一堆互不相关的快照。

### 三个关键设计

**1. 加锁 —— 这个不能省。** 单次采集耗时约 60–160s，而间隔是 15 分钟。一旦某次
超时（比如网络抖动），下一次就会被锁立即拒绝，而不是两个进程同时拉取 37MB 排行榜
并同时往同一个 JSONL 和状态文件里写：

```
17:01:52 === start ===
17:02:04 SKIP: a previous collection run is still in progress   ← 锁生效
```

**2. 钱包缓存的 TTL 必须远大于轮询间隔。** 排行榜响应是 **37MB / 45,138 个账户**，
而采集的是"鲸鱼**持仓**"（每轮都刷新）。钱包**名单**是慢变量，没必要频繁拉。
实测：TTL 900s + 15 分钟轮询 ≈ **2.7 GB/天**；改成 6 小时 → **约 150 MB/天**，
信号新鲜度毫无损失。这就是 `WALLET_CACHE_TTL_SECONDS` 从 900 调成 6 小时的原因。

**3. 故障隔离。** 采集失败不能拖垮决策周期，反之亦然 —— 两个步骤各自记录退出码，
脚本最后以失败数作为退出码返回（cron 已设 `MAILTO=""`，避免无 MTA 时堆积邮件）。

### 运维命令

```bash
./scripts/collect.sh              # 手动跑一轮
./scripts/collect.sh --summary    # 查看累积进度（不写入）

tail -f logs/collect.log          # 运行日志（5MB 自动轮转）
crontab -l                        # 查看已安装的任务
crontab scripts/collect.cron      # 重新安装 / 迁移到新机器
crontab -r                        # 停止采集
```

### 每日汇总（IDE 自动化）

cron 负责采集，但**不会告诉你采到的数据是否健康**。为此配了一条 IDE 自动化
「采集每日汇总」，每天早上运行，产出简报：

- 快照覆盖度（条数 / 跨度 / 是否已可用）
- 决策日志的事件分布
- **采集节奏是否真的做到了**：统计 `=== start` 行数（完整一天应接近 96），
  并列出所有 `SKIP`（某轮超时占用了下一个间隔）与 `FAILED`
- 单轮耗时是否偏离常见的 60–160 秒
- **信号质量**（见下节）

> **匹配陷阱**：统计轮数必须用前缀 `grep -c '=== start'`。日志里真实的开始行是
> `=== start (symbols=BTC,ETH config=...) ===`，带参数 —— 用带结尾的
> `=== start ===` 去匹配会**恒返回 0**，让人误判成「采集从未运行」。这个坑
> 我在写提示词时踩过一次，已写进提示词本身防止被"优化"回去。

这条自动化是**只读**的：不改配置、不重启采集、不写文件。它的价值在于能发现
cron 自己不会报的问题 —— 比如"采集其实已经静默停了两天"，单看 cron 的退出码
是看不出来的（`collect.sh` 在锁竞争时会正常退出 0）。

调度：`FREQ=DAILY;BYHOUR=8;BYMINUTE=0`，按**本地时区**（UTC+8）解析 —— 已实测确认
下次运行落在本地早间而非 UTC 08:00（后者会是本地 16:00）。实际触发时间带有约
2 分钟的调度抖动（实测 07:57），对日报没有影响。

### 当前实测状态

- cron 在 `:00/:15/:30/:45` 准时触发（已验证 17:15:01 那一次完整跑通）
- 单轮耗时：冷启动 ~157s，热路径 ~83–108s，**占用率约 10–17%**
- 每轮约 190 次钱包读取（快照 92 + 决策 92）

### 关于「190 次钱包读取」：不改，但顺带修掉一个真 bug

两个脚本各自独立拉取同一批钱包持仓。**评估后决定不合并**，理由如下（均为实测）：

| 项 | 实测值 |
|---|---|
| 持仓读取耗时 | **51.8s** / 92 个钱包 |
| 每轮重复 | ×2 → 浪费约 52s |
| 占 900s 间隔 | **5.8%** |
| API 速率预算占用 | 全天约 **1%** |

另外实测了两次独立拉取（间隔 2 分钟）的数据：`long_ratio 61.4508` vs `61.45` —— **几乎逐位相同**，
因为鲸鱼持仓在分钟级是粘性的。所以连「两次拉取数据不一致」这个理由也不成立。

**为了省 5.8% 而把交易循环与数据采集耦合起来，是错的权衡。** 保持分离还带来真实的
故障隔离：采集失败不影响决策，反之亦然。

### 但排查过程中发现了一个真 bug：记录器无视配置

`SnapshotRecorder` 构造 `SmartMoneyFactor` 时**只用模块默认值，完全不读配置**。
默认值恰好等于出厂配置，所以一切看起来正常 —— 直到有人调整 `smart_money`：

```
把配置 top_per_window 改成 20:
  配置文件 top_per_window = 20
  记录器   top_per_window = 60   ← 不跟随
```

后果有两层：

1. **记录下来的快照描述的钱包集合不再是策略实际交易的那批** —— 而这份数据的唯一
   用途就是日后回测那个因子。数据错了，回测就失去意义。
2. `logs/smart_money_wallets.json` 的缓存签名包含这些参数 → 签名不匹配 →
   **变成两份缓存，每 6 小时下载两次 37MB**

修复：`SnapshotRecorder` 接受 `config`，并把选币参数**写入每条记录**作为溯源
（`selection` 字段）。这样未来回测能判断两段历史是否由同一套规则产生。

> 这个 bug 能藏住，是因为快照记录器的测试覆盖**为零**。现补 `tests/test_snapshots.py`（19 个用例）。

### 判断"是否已可用"

`--summary` 会直接告诉你：

```
NOT YET USABLE: 0.0 days of history. A smart money backtest needs months, not days.
```

按 15 分钟一轮计算，每天每币累积 **96 条**记录。**需要数月**才够支撑一次
有统计意义的鲸鱼因子回测 —— 这也是为什么应当尽早开始跑。

### `--summary` 的三个部分

一条命令给出全部进展，日报直接消费它的输出：

```bash
./scripts/collect.sh --summary
```

1. **whale snapshots** —— 每币快照条数与跨度
2. **decision journal** —— 事件总数与类型分布
3. **signal quality** —— 前向信号质量（见上一节）

第三部分会**自适应**：还没有方向性信号时，它不打印一堆 `n=0` 的空表，而是一句话
说明「分数从未越过阈值」并只给出门禁分布 —— 那是此时唯一有信息量的数字。
一旦有了方向性样本，命中率、得分分档、置信度分档的表格会**自动出现**。

这个自适应是有意的：日报最怕的是"每天都是一堆看不懂的空表"，那样的监控会被人忽略。

## 回测（已跑，结论为负）

**先说结论：在可回测的那 60% 上，策略没有跑赢随机入场。** 这是 180 天真实数据
（2026-03-21 → 09-17，BTC）的结果：

| 对比项 | 结果 |
|---|---|
| 策略（3%/9% 出场） | **+0.20%** |
| 买入持有 | +8.94% |
| **同配置随机入场 ×50** | 均值 **+3.91%**（p5 +3.06% ~ p95 +4.76%）|
| 策略所处百分位 | **第 0 百分位** |

33 笔交易，胜率 36.4%，盈亏比约 1.8:1，profit factor 1.04 —— **勉强为正，
但低于同配置的随机入场**。

### 对照实验：所有配置都跑不赢自己的随机基准

| 配置 | 策略 | **同配置**随机基准 | 百分位 |
|---|---|---|---|
| 基准 3%/9% | +0.20% | +3.91% | **第 0** |
| **A 无固定止损（ATR 定仓）** | +0.33% | +4.23% | **第 0** |
| B 6%/18% | -1.48% | -1.73% | 第 84（仅 4 笔）|
| C 盈亏比 10:1（3%/30%） | -0.46% | — | — |

**每一个配置都落在各自随机基准的第 0 百分位。** 这是一个稳健的负面结论：
方向判断没有可证明的信息量。注意策略的绝对收益在「无固定止损」下会改善，
但**随机入场改善得更多**，所以百分位不动 —— 只看绝对收益会得出错误结论。

### 两个方法论要点

**1. 随机基准会随出场配置大幅漂移。** 同一份数据上，随机入场的均值在
+3.9% ↔ −1.7% 之间摆动，完全取决于止损/止盈设置。所以「是否跑赢随机」
**只能在同一配置内比较**；跨配置比百分位会得出完全相反的结论
（变体 B 单看是「第 84 百分位」，但它只有 4 笔交易）。

**2. 固定 3% 止损对 BTC 过窄。** BTC 的日常波动就能打穿 3%，止损被噪声反复触发。
改用 ATR 定仓后胜率从 36.4% 升到 38.7% —— 但百分位不变。

### 修复了一个保真度缺陷：反转平仓

回测原先**只在空仓时生成信号**，所以持仓只能靠止损/止盈退出。而实盘
（`agent/bot.py` 的 `run_cycle`）每轮都生成信号，遇到反向信号会**平仓并反手**。

修复前后的对比：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 净值 | -0.86% | **+0.20%** |
| 胜率 | 22.2% | **36.4%** |
| 每笔期望 | -0.32 | **+0.06** |
| 最大回撤 | 3.91% | **2.22%** |
| **信号评估次数** | **537** | **4287**（≈4320 根 bar）|

最后一行是关键：修复前 4320 根 bar 里只评估了 537 次信号 —— 不只是缺反转平仓，
连 `signals_seen` 和门禁拒绝统计都是错的。修复后门禁分布才有意义
（`threshold 3192 / already holding 939 / cooldown 73 / confidence 38 / halted 38`）。

**但这个修复没有改变结论** —— 百分位仍是第 0，因为随机基准同步上升。

### 必须说明的局限

- 样本小（33 / 31 / 4 笔），`metrics.py` 自己就会警告 <30 笔不具统计意义
- 180 天是**单一上涨行情**（买入持有 +8.94%）
- **40% 的鲸鱼因子是关闭的** —— 这测的是 60% 的模型，不是部署中的策略
- 配置里 `take_profit_pct: 9.0` 的注释写着「matching Fox's asymmetry」，但 Fox 的
  设计是**平均盈利 = 平均亏损的 10 倍**（43% 胜率即可盈利）。当前 3:1 需要 >25%
  胜率，实测 36.4% 虽已超过，但整体仍无边缘。**注释与所引设计不符。**

### 这些结论意味着什么

若可回测的 60% 没有边缘，那么整个策略的收益**完全押在那 40% 的鲸鱼因子上** ——
也就是证据最薄弱、还要等数月才能回测的那个部分。这不是「等数据」的理由，
而是「尽快验证全模型」的理由。

## 前向信号质量分析

`analyze_signals.py` 回答回测回答不了的问题：**live 信号（含鲸鱼因子）到底有没有预测力。**

它不需要等数月。按 96 个信号/天，**两周约 1300 个样本**就足以对「方向有没有信息量」
给出第一个读取。这正是它比回测更快的原因 —— 回测只能测 60%，而它测 100%。

```bash
python analyze_signals.py                          # 默认 1h/4h/24h 前瞻
python analyze_signals.py --horizons 4,12,48
python analyze_signals.py --max-gap-minutes 60     # 容忍更大的采集间隔
```

### 两个刻意分开的问题

**1. 信号能否预测？** —— 用**全部**信号测，包括被门禁拒绝的。这是更根本的问题，
所需样本也最少。中性信号不计入（它们本就没有方向），而不是当作猜错。

**2. 门禁是否过严？** —— 被拒绝的信号是一组**免费对照组**。如果被挡掉的信号事后
显著命中，说明门禁在挡有效信号。报告会按门禁归类给出各自的前瞻命中率。

### 几个实现细节

- **价格序列取自 journal 本身**（每条 signal 都记录了决策时刻的 mark price），
  所以不需要联网，也不可能与 agent 当时看到的价格不一致
- **前瞻价格必须落在目标时刻附近**（默认 ±30 分钟）才采用。采集会暂停、会漏跑，
  拿一个过期价格当前瞻收益会**凭空造出优势**
- **尚无前瞻数据的信号会被跳过**，而不是拿现有数据凑 —— 否则最近几根 bar 的
  涨跌会系统性污染结果
- **门禁原因先归一化再聚合**。原始文本带变量（`cooldown active, 239 min remaining`、
  `halted for another 187 min`），直接计数会让几乎每条独立成行，分布完全看不出来
- 报告会显式标注 `|z| >= 1.96` 才算 95% 置信，且 n<30 一律判为「样本不足」

## 回测

```bash
python run_backtest.py                        # 200 天，含基准对照
python run_backtest.py --days 90 --random-runs 100
python run_backtest.py --no-benchmark         # 只看策略
```

回测**复用真实的因子、纪律层与头寸计算**（`Synthesizer` / `Discipline` / `compute_size`），
不重新实现策略逻辑，避免两套代码漂移。

### 关键限制：聪明钱因子无法回测

公开 API 不提供历史鲸鱼持仓，所以**占 40% 权重、也是唯一有证据支撑的因子无法参与回测**。
回测会强制关闭 `require_smart_money_alignment`（否则 100% 信号被拦），
并在输出顶部和 CAVEATS 里明确标注。

**所以回测结果只反映剩下约 60% 的模型，不代表实盘策略。**

### 实测结果：跨币种交叉验证（200 天，$1,000 起始）

| 币种 | 收益 | 交易 | 胜率 | expR | PF | 买入持有 | 随机均值 | 随机分位 |
|---|---|---|---|---|---|---|---|---|
| BTC | **-2.40%** | 32 | 18.8% | -0.075 | 0.68 | +14.31% | +1.86% | 0 |
| ETH | +3.97% | 38 | 34.2% | +0.104 | 1.51 | +23.17% | +3.11% | 65 |
| SOL | +1.49% | 57 | 28.1% | +0.027 | 1.12 | +17.42% | -1.48% | 100 |

**结果在币种间不一致，且没有任何组合跑赢买入持有。**

### 出场结构的数学性质

止损 3% / 止盈 9%（盈亏比 3:1）时，随机游走下先触止盈的概率为
`3/(3+9) = 25%`，恰好等于打平所需胜率 —— **该结构在无方向信息时期望值精确为 0**，
计入成本后必为负。实测胜率在 18.8%-34.2% 之间围绕 25% 波动，与「无信息」一致。

### 因子消融：市场因子是负担

| 配置 | BTC | ETH | SOL |
|---|---|---|---|
| 技术+市场（当前） | -2.40% | +3.97% | +1.49% |
| **仅技术** | **+2.44%** | **+5.89%** | **+1.90%** |
| 仅市场 | 0.00%（0笔） | +0.27%（3笔） | +0.57%（2笔） |

仅技术在三币种上全部优于当前配置，说明**资金费率逆向因子在拖后腿**。

### 但该发现未通过样本外检验

把 200 天拆成前后两半，用「仅技术」配置：

| 币种 | 样本内胜率 / 盈亏 | 样本外胜率 / 盈亏 |
|---|---|---|
| BTC | 40.0% / +26.11 | 23.1% / **-1.69**（翻负） |
| ETH | 37.0% / +37.26 | 32.0% / +21.59 |
| SOL | 31.0% / +18.16 | 25.8% / **+0.81**（归零） |

样本外胜率收敛到 23-32%，即 25% 盈亏平衡点附近。**「仅技术更好」是样本内过拟合。**

### 资金费率套利也不成立

| 币种 | 均值 bp/h | 年化 APR | >0 占比 |
|---|---|---|---|
| BTC | 0.051 | **4.5%** | 75.7% |
| ETH | 0.059 | **5.1%** | 78.9% |
| SOL | -0.014 | **-1.2%** | 57.2% |

delta 中性需 50/50 分配资金，净年化仅约 **2-2.5%**，且承担基差、强平与交易所风险。

### 突破：聪明钱历史可以被重建

最初结论是「聪明钱因子无法回测，需等数月快照」。**这是错的** —— 我只查了
`clearinghouseState`（仅当前状态），漏掉了历史端点。

`userFunding` 的每条记录都带 `szi`（当时的持仓数量）：

```json
{"time": 1771891200000, "delta": {"coin":"ETH","szi":"-5.7725625","fundingRate":"0.0000090922"}}
```

用它 + 游标分页，可以重建每个钱包的历史持仓序列：

```bash
# 采集（约 3-4 分钟，250 个候选账户）
# 内置于 backtest/whale_history.py
```

**实测采集结果**：87-103 个钱包可用，10,612 个持仓点，覆盖 2025-08 → 2026-09（13 个月）。

### 数据粒度的真相

**关键发现**：funding 记录是**日级**，不是小时级（中位间隔 24h，仅 41% 间隔 ≤6h）。
这直接决定样本量：

| 陈旧窗口 | 平均持仓钱包数 | 有数据的时间占比 |
|---|---|---|
| 6h | 1.3 | **仅 12%** ← 不可用 |
| 24h | **21.6** | 100% |
| 48h | 23.9 | 100% |

之前观察到的「越陈旧越好」不是陈旧起作用，而是**覆盖率**：6h 时因子基本处于
「无数据」状态。

### 含聪明钱因子的回测结果（三币种交叉验证，200 天）

| 币种 | 配置 | 收益 | 交易 | 胜率 | expR | PF | 样本外盈亏 | 随机分位 |
|---|---|---|---|---|---|---|---|---|
| BTC | 不含 | -2.40% | 32 | 18.8% | -0.075 | 0.68 | — | — |
| BTC | **含** | **+3.30%** | 24 | **37.5%** | +0.137 | 1.70 | +9.70 | 90% |
| ETH | 不含 | +3.97% | 38 | 34.2% | +0.104 | 1.51 | — | — |
| ETH | **含** | **+7.61%** | 30 | **46.7%** | +0.247 | 2.50 | +53.32 | 93% |
| SOL | 不含 | +1.49% | 57 | 28.1% | +0.027 | 1.12 | — | — |
| SOL | **含** | +1.29% | 42 | 28.6% | +0.032 | 1.14 | +8.66 | 100% |

3/3 币种胜率提升或持平，样本外盈亏全部为正，随机分位 90-100%。

### 关键控制实验：排除「只是减少交易」

交易数从 32→24、38→30、57→42 都在下降。**如果基础信号是负期望的，任何减少交易的
过滤都会「改善」结果**，那就不说明聪明钱有信息量。用**随机同意/反对**的顾问
替换聪明钱意见（相同门禁、相同结构）作为对照：

| 币种 | 真实聪明钱 expR | 随机顾问 expR |
|---|---|---|
| BTC | **+0.121** | -0.014 |
| ETH | **+0.086** | +0.072 |
| SOL | **+0.089** | +0.030 |

**每笔期望值 3/3 优于随机顾问** —— 说明是信息量而非交易数减少。
但 ETH 的总收益随机顾问反而更高（+3.62% vs +2.84%），且 ETH 的 expR 差距在噪声内。

### 结论：是目前唯一的正向线索，但未证实

支持它的证据：跨 3 币种一致、样本外保持、随机方向分位高、每笔期望值优于随机顾问。

**仍不足以支撑实盘**：

1. **不显著**：随机分位 90/93/100% 在 30 次采样下约 p 0.03-0.10，
   且经过多轮比较后削弱
2. **回测的不是要跑的东西**：回测用 24h 陈旧持仓，线上读**实时**持仓
3. **样本小**：每币种仅 24-42 笔，单周期
4. **覆盖率不完整**：BTC 103 / ETH 62 / SOL 73（候选 250）

### 总结论（最终）

| 方向 | 结论 |
|---|---|
| 技术 + 资金费率方向预测 | 无 edge，样本外不成立 |
| 市场因子（资金费率逆向） | 有害，拖累表现 |
| 资金费率套利 | 净约 2% APR，不值得 |
| **聪明钱因子** | **唯一正向线索，跨币种一致，但未证实** |

**不建议实盘。** 唯一合理的下一步是让 Agent 以 dry-run 跑起来积累
**实时**信号的验证记录 —— 因为线上数据（实时持仓）严格优于回测数据（24h 陈旧），
而这是回测无法回答的部分。

### 数据边界

| 数据 | 可用范围 |
|---|---|
| 1h K 线 | 约 **208 天**（受 5000 根上限约束） |
| 4h K 线 | 1 年以上 |
| 每小时资金费率 | 与 K 线同期 |
