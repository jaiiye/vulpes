# Vulpes

**一个高选择性的 Hyperliquid 合约交易 Agent。** 名字取自狐属（*Vulpes*）：
狐狸耐心、善于观察、极少出手 —— 正对应它的核心立场，
**盈利来自拒绝信号的能力，而不是信号的数量**。

它最小但完整，把三件事拼在一起：

| 来源 | 借鉴的东西 |
|---|---|
| ZoneIn 多因子合成器 | 聪明钱 40% + 技术 35% + 市场 25% → 0-100 得分 → 离散信号 |
| chainstacklabs/hyperliquid-trading-bot | YAML 配置驱动、测试网默认、优雅退出、风控开关 |
| Senpi 22-Agent 实盘实验（Fox） | 选择性执行、频率上限、冷却期、趋势过滤、禁止自我调整 |

**核心立场**：策略内核不是网格，而是"高选择性 + 聪明钱对齐"。22 个 Agent 的实盘数据表明，
盈利来自**拒绝信号**的能力，不是信号的数量。

## 三因子合成

| 因子 | 权重 | 读什么 | 如何打分 |
|---|---|---|---|
| 聪明钱 | 40% | 排行榜 Top N 账户在目标币的实时持仓 | 多头名义占比，50% 为中性，放大 1.6x |
| 技术 | 35% | Supertrend / EMA / RSI / ADX（1h + 4h） | 加权混合，ADX 决定趋势可信度 |
| 市场 | 25% | 资金费率 / 持仓量 / 24h 涨跌 | 拥挤度（逆向）+ 动量，按资金费率强度调权 |

### 置信度处理

关键设计：**置信度为 0 的因子不贡献中性分 50，而是把权重让给有数据的因子。**

这意味着不会因为某个数据源挂掉就把信号稀释成"看起来中性"。代价是信号建立在更少的输入上，
所以纪律层另外强制要求聪明钱对齐，而不是单纯信任混合分。

### 聪明钱因子的选钱包逻辑

这是全项目最反复打磨的部分，结论来自实测而非直觉。

**问题**：直接取排行榜单一窗口的 top-N 是运气污染的代理变量。实测主网数据，
`week` 与 `month` 的 top-25 集合只有 **11% 重合**（Jaccard 0.111）。

**方案**：对多个窗口分别排名并取并集，用「持续性」（出现在几个窗口中）加权。

关键实测对比（BTC，同一时刻）：

| 方案 | 采样钱包 | BTC 持仓者 | 多头名义 | 最大单仓占比 |
|---|---|---|---|---|
| 单窗口 top25 | 25 | 10 | $3.8k | 43.6% |
| 并集 + 持续性**硬过滤**≥2 | 52 | **3** | — | 45.6% |
| **并集，持续性作权重** | 118 | **18** | **$149M** | **27.9%** |

**重要发现：把持续性当硬过滤条件反而有害。** 能跨窗口持续排名的钱包多为
$1B 级的大型多元账户，往往在特定币种上并无持仓；而真正持有该币种的
方向性交易者通常只出现在单个窗口里。所以持续性在这里用作**权重**
（3 窗口钱包的名义按 3 倍计），而不是筛选门槛。

净效果：持仓样本 10 → 18，单仓集中度 43.6% → 27.9%，名义金额量级恢复正常
（原来的 $3.8k vs $1.0M 是明显失真的）。

如果确实想要更小更严格的集合，把 `min_persistence` 设为 2 即可，但要接受覆盖率的损失。

## 风险控制

头寸按风险预算计算，而不是固定名义金额：

```
stop_distance = 1.5 × ATR          （或 stop_loss_pct 指定的距离）
risk_usd      = equity × risk_per_trade_pct
size_by_risk  = risk_usd / stop_distance
size_by_alloc = (equity × account_allocation_pct) / price
size          = min(size_by_risk, size_by_alloc)
```

波动大的标的自动作小仓位。这是"每笔风险 2%"成为真实约束而非装饰的关键。

配置层的硬性拒绝：

- 杠杆 > 10x 直接拒绝（对应 Dire Wolf 的 25x 自杀式加仓）
- 主网实盘必须显式指定 `risk_preset`，且杠杆 ≤ 3x
- `dry_run: false` 但没有私钥 → 拒绝启动
- `safety.hard_stop_pct` 必须 ≥ `risk.stop_loss_pct`，否则安全垫会先于止损触发
- `take_profit_pct` 必须 ≥ `stop_loss_pct`，否则是负期望
- 未知配置键直接报错（拼错 `max_signals_per_day` 不会被静默忽略）

### 最大回撤保护

`risk.max_drawdown_pct` 会跟踪峰值权益，回撤触及上限时**停机且不再开新仓**。
停机状态**持久化到磁盘**，重启不能绕过 —— 否则「重启进程」就成了绕过风控的手段。

### 护栏跨重启

当日交易次数、冷却期、连亏熔断、持仓状态全部持久化在 `logs/agent_state.json`：

```bash
python run_bot.py --show-state    # 查看当前状态
python run_bot.py --clear-halt    # 解除停机（仅解决根因后使用）
```

这一条至关重要：**「限制交易频率」是本项目唯一有证据支撑的 edge**，如果重启就归零，
那等于没有护栏。

## 资金安全机制

以下每一条都对应一个真实发现并修复的缺陷，不是理论防御。

### 1. 保护单失败立即平仓

开仓后若止损单挂失败，会**立即市价平仓**。若平仓也失败，则记录该仓位（以便继续尝试管理）
并**停机**，要求人工介入。

绝不允许出现「仓位在交易所存在、程序却不知道」的裸仓。

### 2. 限价单未成交不算持仓

只检查订单返回的 `error` 是不够的 —— 未成交的挂单返回 `{"resting": ...}`。
把挂单当成成交会产生**幽灵仓位**（追踪一个不存在的敞口，之后还会「平掉」它）。

现在的流程：提交 → 解析 `filled`/`resting`/`error` → 若是 `resting` 则有界等待，
超时**撤单并放弃本次入场**，不创建 Position。

### 3. 启动时对账

启动时用交易所的真实持仓与本地状态比对，四种情况都被显式处理：

| 本地 | 交易所 | 处理 |
|---|---|---|
| 空仓 | 空仓 | 无事 |
| 空仓 | **有仓** | 孤儿仓 → 接管并告警（检查是否有保护单） |
| 有仓 | **空仓** | 幽灵仓 → 清除 |
| 有仓 | 有仓但**不一致** | 以交易所为准并告警 |

对账读取失败时**拒绝交易**，而不是当成「空仓」继续 —— 后者正是孤儿仓被忽略的原因。

### 4. 异常不再终止循环

主循环捕获所有异常并计数，连续 5 次失败则停机。此前只捕获两类异常，
其他异常会直接杀死进程。

## 数据源设计：为什么聪明钱永远读主网

**`testnet` 只控制订单发往哪里，不控制信号从哪读。**

聪明钱因子（权重最高，40%）始终从主网读取鲸鱼数据，原因是一个实测出来的 bug：
排行榜返回的是主网账户地址，但如果用测试网 API 去查这些地址的持仓，会全部返回空 ——
测试网上没有鲸鱼。这会让最高权重的因子静默归零，信号却看起来"正常"。

修复前实测：25 个钱包采样，**0 条持仓**。修复后：**10 条真实持仓**。

日志里每个信号都会标注 `data_network`，避免这个歧义再次出现。

## 性能

首次运行需要下载排行榜（**37 MB / 45,138 个账户**，接口不支持服务端限量），
因此做了两层缓存：

| 阶段 | 耗时 |
|---|---|
| 首次运行（下载 37MB + 解析） | ~28-47s |
| 后续进程（命中磁盘缓存，`logs/smart_money_wallets.json`） | **0.1s** |
| 单轮循环，冷启动（含 118 个钱包持仓读取） | ~41s |
| 单轮循环，热路径 | ~18s |

持仓读取是独立 HTTP 请求，已改为并发（12 线程）。串行 25 个钱包实测 58s，
并发后大幅缩短。多窗口并集把候选池从 25 提升到 118，代价是读数变多，
换来的是持仓样本 10 → 18 和集中度 43.6% → 27.9%。

磁盘缓存按「配置签名」校验（窗口列表、取样数、持续性阈值、白/黑名单），
配置一变缓存自动失效，不会读到过期的选择结果。

每轮 18-41s 的工作量，配合 300s 轮询间隔，占用率约 6-14%。这不是一个剥头皮机器人。

## 代码审查发现并修复的缺陷

一轮系统性审查（重点放在资金安全路径）发现并在修复前**全部有测试复现**的问题：

### 🔴 挂单永远不会被撤销（最严重）

`self._last_result` 被初始化为 `None` 却**从未被赋值**，导致 `_last_order_id()`
永远返回 `None`：

1. 限价单挂出 → 交易所返回 `{"resting": {"oid": 123}}`
2. `_resolve_resting_order` 拿不到 oid → **立即返回，既不等待也不撤单**
3. `open_position` 抛出「did not fill **and was cancelled**」

**订单从未被撤销。** 它仍挂在盘口，随时可能成交 —— 而程序认为自己空仓。
结果是**无止损、无止盈、无人管理的孤儿仓位**，日志还在说谎。`order_type: limit`
是默认配置，所以这是默认路径。

**根因是测试覆盖为零**：`resting` / `_last_order_id` / `_cancel_order` 一个测试都没有，
所以 204 个测试全绿也没抓到。现已补 `tests/test_execution.py`（26 个用例）覆盖
整条挂单生命周期。

修复后语义更严格：**只有交易所状态确认撤销，才报告为已撤销**；
撤销无法确认时抛 `CriticalExecutionError` 直接停机，而不是继续在未知敞口下交易。

### 🟡 反转平仓失败 → 旧仓位被孤儿化

`close_position` 失败时静默返回，但主循环继续开新仓并覆盖 `self.position`，
旧敞口从此无人管理。现在 `close_position` 返回布尔值，主循环在平仓失败时
**放弃本轮入场**。

### 🟡 审计日志失真

`order_filled` 事件里 `requested_size` 和 `filled_size` 都是覆盖后的值，
原始请求量丢失，无法审计部分成交。现已分别记录。

### 🟡 定仓提示与算式自相矛盾

日志输出「10% of $1,000 = $100 **at 2x**」，暗示名义价值是 $200，
但代码实际把 notional 限制在 $100。杠杆限制的是保证金而非名义价值。
现改为如实说明 notional 与所需保证金。

### 🟡 挂单参数会静默改变选币语义

`top_traders` 走旧的单窗口路径，会**静默把三窗口并集坍缩成单窗口**，
与 `top_per_window` 语义冲突。项目无外部用户，已直接移除该兼容参数
（配置写错应当显式报错，而不是静默降级）。

### 🟢 其余清理

- 删除死代码：`DEFAULT_TOP_TRADERS`、`self.top_traders`、`close_position` 中未使用的 `is_buy`
- `HyperfeedSource` 此前绕过 `http_util`，无重试/截断/体积上限保护；
  现统一走 `request_json`（新增 `headers` 参数以支持 Bearer token），
  且不再把钱包地址截断到 12 字符（那会破坏钱包身份标识）
- 魔数收敛为常量：`FALLBACK_STOP_FRACTION`、`TAKER_FEE_RATE`、`SMALL_NOTIONAL_USD`、
  `SNAPSHOT_REUSE_SECONDS`
- ATR 回退此前在 3 条路径中有 2 条静默降级，现全部记录到 notes
- R:R 提示此前只对 LONG 计算（做空缺提示）；改为对多空对称
- 修正 `_cancel_order` 的错误签名回退 —— 它曾尝试
  `cancel(symbol, (oid, symbol))`，把元组当成订单 id 传递，永远不可能成功

## 回测层审查发现并修复的缺陷

第二轮审查转向 `backtest/`（约 1900 行）。**先说结论：反未来函数的设计是正确的** ——
`BacktestMarket` 用 `bisect_left` 划定「只返回已收盘 bar」的边界，指标与因子在
bar T 的开盘时刻只看得到 T 之前的数据，成交在 T 的开盘价，这是标准的
「收盘决策 / 开盘成交」约定，不存在未来函数泄漏。这部分实现和注释都准确。

但发现了几处会**系统性美化或偏离结果**的问题：

### 🟡 止损成交价忽略跳空（会美化回测结果）

`_manage` 里止损触发时直接用 `pos.stop_price` 作为成交价。可是如果这根 bar
**开盘就已经跳空越过止损**，根本不可能在止损价成交 —— 实际成交价应该是开盘价。

```python
# 修复前：bar 从 90 开盘、止损 97，却按 97 记成交
self._close(ts, pos.stop_price, "stop loss", bar)
# 修复后
self._close(ts, min(pos.stop_price, bar.open), "stop loss", bar)   # 多头
self._close(ts, max(pos.stop_price, bar.open), "stop loss", bar)   # 空头
```

这是回测最不能出错的方向：**每次都按理想价格止损，等于高估了所有被止损的交易**。
止盈侧保持按目标价成交不变 —— 跳空穿过止盈是有利的，按目标价记反而是保守的。

### 🟡 回测置信度系统性偏离实盘

`HistoricalSmartMoney` 无法重建每个钱包的未实现盈亏（资金费历史里没有开仓价），
于是 `unrealized_pnl` 全是 0。而实盘 `evaluate` 用它算 `winner_ratio`：

```python
winner_ratio = 盈利钱包数 / 总数        # 回测恒为 0
quality_conf = 0.5 + 0.5 * winner_ratio # 因此恒为 0.5（该项下限）
```

实测偏差 **0.075**，且**足以跨越 `min_confidence` 阈值改变交易决策**。回测永远
按「所有鲸鱼都刚好不赚不亏」这个最悲观假设打分。

修复：给快照加 `pnl_available` 标记，不可知时把该项取**区间中点**而不是最小值。

我最初写的是「丢弃该项、其余权重重归一化」，**实测后发现是错的**：

| 方案 | 置信度 | 是否落在实盘区间 `[0.450, 0.525]` |
|---|---|---|
| 旧行为（当作 0 已知） | 0.4500 | 区间**边缘**（悲观端） |
| 丢弃 + 重归一化（错误方案） | 0.4412 | **区间外**，反而更偏 |
| 取中点（最终方案） | **0.4875** | **区间正中**，上下偏差对称 ±0.0375 |

丢弃一项会把权重错误地转移给不相关的因子，所以「少用一项信息」并不等于「中性」。
只有取该项自身区间的中点才是无偏的。这个教训比修复本身更值钱 ——
我差点把一个看起来合理、实测更糟的方案当成改进交出去。

### 🟡 归一化参数硬编码

`persistence_window_count=3` 是写死的，而它是 `curation_score` 的分母
（`persistence_window_count` 也是 `SmartMoneySnapshot` 的字段）。如果实盘配置
`windows` 不是 3 个，回测的 curation 与置信度就会和实盘不一致 —— 而
`engine.py` 的设计前提正是「回测与实盘走同一套决策代码」。现已从配置读取。

### 🟡 `CandleSeries` 一半公开、一半私有

容器只公开了 `closes`/`highs`/`lows`，缺 `opens`/`times`/`volumes`，
于是回测代码只能伸手取 `series._times`、`part._opens` 等私有字段（共 9 处）。
补齐公开访问器并全部改用，同时加了一条**扫描源码**的回归测试防止退回。

### 🟢 其余清理

- `funding_at_ms` 每次调用都重建时间戳列表，是 O(n) 而非注释声称的 O(log n)。
  现由 loader 构建一次索引，并让 `funding_between` 用 `bisect` 划定区间而非全表扫描
- `_try_enter` 中 `open_position`/`is_reversal` 恒为 False/0（该方法只在空仓时调用）
- `run()` 的 if/else 两个分支都调用 `set_now(ts)`，已合并

### 打分解耦：消除 `__new__` 绕过构造器

回测此前用 `SmartMoneyFactor.__new__(SmartMoneyFactor)` 造一个**半成品实例**，
再手工补上 `evaluate` 恰好会读到的那一个属性，借此复用实盘打分逻辑。

它能跑，但**没有任何测试能阻止它变脆**：一旦 `evaluate` 新增一处 `self.xxx` 依赖，
回测会在运行时抛 `AttributeError`，而实盘与全部测试依然全绿 —— 缺陷只在一个
人恰好去跑回测时才暴露。

现已把打分逻辑从 `SmartMoneyFactor.evaluate` 抽成**模块级纯函数**：

```python
def score_snapshot(snapshot, symbol=None, data_network="mainnet") -> FactorScore
```

- 纯函数：无 I/O、无实例状态，`data_network` 从实例属性变成显式入参
- `SmartMoneyFactor.evaluate` 退化为薄包装：**只负责取快照，然后交给纯函数**
- `HistoricalSmartMoney.evaluate` 直接调用同一个纯函数，不再需要任何实例
- 顺带把散落的魔数收敛为具名常量（`WEIGHT_*`、`SAMPLE_SIZE_SATURATION`、
  `LEADERBOARD_CONF_CAP_*`、`WALLET_ERROR_CONFIDENCE_PENALTY`）

**两条路径的一致性现在由结构保证，而不是靠约定**。并加了三条测试固化：

| 测试 | 保证 |
|---|---|
| `test_live_evaluate_delegates_to_the_shared_scorer` | 实盘输出与纯函数调用**逐字段相同**（score/confidence/reasons/details）|
| `test_backtest_evaluate_delegates_to_the_same_scorer` | 回测输出与纯函数调用逐字段相同 |
| `test_production_code_does_not_bypass_constructors` | 源码级扫描，`__new__(` 不得再次出现 |

这是本次审查里我认为最有价值的一处改动：它把一个**「当前正确但无保护」**的
隐式契约，变成了**「结构上不可能违约」**的显式接口。

### 已知局限（已识别，刻意未改）

这两项不是 bug，而是有意的取舍，写在这里以免被误认为已解决：

1. **回测未建模滑点。** `ASSUMED_SPREAD_BPS = 2.0` 只用于盘口价差告警，
   从不进入盈亏计算。回测的执行成本只有手续费 + 资金费。对低频策略影响有限，
   但任何"边缘很薄"的结论都应当打折扣看。

2. **入场那根 bar 的区间不参与出场判定。** `_manage` 在 `_try_enter` 之前执行，
   所以 bar T 开盘建仓后，第一次出场检查发生在 T+1。若止损在 T 之内被打穿，
   回测会继续持有 —— 实盘不会。这是双向误差，不单方向美化，但确实是偏离。

## 测试套件审计：哪些测试真正承重

测试数量本身不是指标 —— **测不出问题的测试等于零**。用变异测试实测：
故意破坏 9 处生产行为，看哪些测试会失败。

### 第一次结果：2 个变异存活

| 变异 | 捕获 |
|---|---|
| 回测止损忽略跳空 | ✅ 1 个测试 |
| 挂单 oid 不再被记录 | ✅ 2 个测试 |
| 非有限浮点不再被拒绝 | ✅ 4 个测试 |
| **固定临时文件名（并发）** | ❌ **0 —— 存活** |
| 平仓失败仍报成功 | ✅ 1 个测试 |
| **持仓方向符号丢失** | ❌ **0 —— 存活** |
| 冷却期永不生效 | ✅ 2 个测试 |
| 置信度丢掉盈利占比 | ✅ 2 个测试 |

### 存活 1：我自己上一轮加的并发测试是废的

它的断言是「没有异常逃逸」+「文件仍可解析」。但 `save()` 会把
`os.replace` 的失败**吞成 `False`**（`except OSError: return False`），
所以固定临时文件名导致的写入失败**根本不会抛异常** —— 测试无论如何都通过。

修复：断言**每个写入者都返回 True**。这才是能区分两种实现的断言。

### 存活 2：仓位方向的符号约定完全没有测试

`size` 承载方向，`notional` 必须与它同号。而消费方**显式取负**：

```python
239:        return sum(-p.notional for p in self.shorts)
```

符号一旦丢失，`short_notional` 由 +60 变成 **−60**，
`long_ratio_pct` 从 62.5% 变成 **250%** —— 因子会把一个**重度做空**的市场
读成**多头共识**。这是打分链路的主输入，却没有任何测试保护。

**根因**：测试全部用 `WalletPosition(...)` **直接构造**一致的数据，
从未执行产生符号的**解析代码**。而该约定在两处被逐字重复
（`abs(notional) if size > 0 else -abs(notional)` × 2），
散落意味着没有单一可测的锚点。

修复：提取 `signed_notional(notional, size)`，约定只说一次；
新增 `TestNotionalSignConvention`，既测辅助函数，也**驱动真实解析器**
（stub 掉 `request_json`）验证交易所载荷中的无符号 notional 被正确赋予符号。

### 第二次结果：9/9 全部捕获

| 变异 | 捕获（修复后） |
|---|---|
| 固定临时文件名 | ✅ 1（且实测稳定：正确代码 20/20 通过，变异代码 10/10 捕获） |
| `signed_notional` 函数体去符号 | ✅ 3 |
| 调用方绕过 `signed_notional` | ✅ 1 |
| 其余 6 项 | ✅ 均保持捕获 |

### 关于「327 个是否都需要」

实测数据：**62 个类、平均 5.3 个用例**，无上帝类；**无断言的测试 0 个**、
**完全重复的测试体 0 组**；全套 **4.2 秒**跑完（其中回测占 3.3 秒）。
随机抽查最大的 `TestLeaderboardParsing`（16 个），覆盖的是
「解析嵌套载荷 + 多窗口并集 + 持续性加权 + 排序」四个不同行为，不是凑数。

结论：**没有需要删的测试，但有 2 个需要修的** —— 一个测不出问题（已修），
一个本该存在却缺失（已补）。数量不是问题，**能不能失败才是**。

## 第四轮审查：崩溃恢复路径（`agent/state.py`）

这是全项目唯一只被间接覆盖的关键防线 —— 它决定「进程被杀死后能否正确恢复」。
先说**验证为正确的部分**，再说问题。

### 审查确认无问题的部分

- **启动对账的四种情形齐全**：跟踪空/交易所有 → 采纳；跟踪有/交易所空 → 清除；
  两者都有但不一致 → **采信交易所**并记事件；一致 → 仅记录。对账失败时抛
  `CriticalExecutionError` 拒绝交易，而不是猜测。这是正确且保守的设计。
- **`shutdown()` 刻意不强制平仓** —— docstring 的理由充分：每次重启都变成市价单
  比留一个待恢复的仓位更糟。
- **`peak_equity` 确实随状态持久化**（经 `asdict()`）。

> 最后一条值得记录：我最初怀疑 `_persist()` 漏写了 `peak_equity`（该函数逐字段
> 赋值，确实没有它），差点作为 bug 上报。**实测发现它经 `asdict()` 正常往返** ——
> 因为 `check_drawdown` 直接写在 `self.state` 上，序列化的是整个对象。
> 如果只靠读代码，这会是一次误报。

### 🟡 非有限浮点会静默废掉守卫

`_as_float` 接受 `inf`/`nan`，而它们的**所有比较都为假**：

| 字段被污染为 | 失效的守卫 | 原因 |
|---|---|---|
| `peak_equity = inf` | 回撤熔断 | `(inf - equity)/inf = nan`，`nan >= limit` 为假 |
| `last_trade_ts = nan` | 冷却期 | `(now - nan) < cooldown` 为假 |
| `halted_until = nan` | 连亏熔断 | `now < nan` 为假 |
| `trades_today = nan` | 每日上限 | 计数比较为假 |

危险之处在于**守卫看起来还在，只是永远不触发** —— 没有任何报错。

而且这是**自洽的污染路径**：`json.dumps` 会把 `inf` 写成 `Infinity`
（**非法 JSON**），`_as_float` 又能把它读回来。已实测确认。

修复：新增 `_finite()`，非有限值一律拒绝；`save()` 用 `allow_nan=False`，
宁可写入失败（保留上一个有效文件）也不污染下次启动。

### 🟡 固定临时文件名 → 并发写会互相污染

```python
tmp = self.path.with_name(self.path.name + ".tmp")   # 两个进程共用同一个文件
```

这个项目**明确支持两个进程并存**（cron 每 15 分钟一个周期进程 + 手动运行，
README 里还专门警告过）。两者同时写会交错进同一个临时文件，
再由 `os.replace` 把混合物发布成正式状态 —— 而损坏的状态文件 `load()` 返回
`None`，**一次性重置全部护栏**。

修复：改用 `tempfile.mkstemp()` 为每个写入者分配独立临时文件。
实测 24 个线程并发写入：无异常、无残留临时文件、文件始终可解析。

### 🟢 docstring 承诺超出实现（缺 `fsync`）

原文写「临时文件 + rename 使崩溃不会留下损坏文件」。这对**进程崩溃**成立，
对**断电/硬重启**不成立：rename 可能已持久化而数据还在页缓存里。已补
`flush() + fsync()`，并修正文档措辞。

### 🟢 裸 `assert` 记录不变量

`reconcile_startup` 用 `assert live_pos is not None and ...` 收窄类型。
`-O` 下断言被剥离，后续代码会直接解引用 `None`。虽因前置分支的穷尽性当前无害，
但已改为显式守卫。

### 验证

- **327 个测试通过**（+8），新增覆盖：inf/nan 在各字段被拒绝、
  `save` 拒绝写入非有限值且保留旧文件、落盘文件通过**严格** JSON 校验、
  24 线程并发写不损坏不残留
- 端到端正常，无残留临时文件，零 lint

## 开发中实测发现并修正的陷阱

这些全部是先跑出问题、再定位、再补回归测试，值得记录：

1. **`openInterest` 是币数量，不是美元。** 主网 BTC 返回约 37,400，
   乘以 markPx 约 $77k 得到 $2.9B 才符合常识。最初按美元处理，算出 $0.0M。
   现通过 `AssetContext.open_interest_notional` 转换。

2. **排行榜不在 `/info` 端点。** `{"type":"leaderboard"}` 稳定返回 HTTP 422。
   正确地址是 `https://stats-data.hyperliquid.xyz/Mainnet/leaderboard`，
   返回 `leaderboardRows` + `windowPerformances`。

3. **37MB 响应会导致传输截断。** `http.client.IncompleteRead` 被当作致命错误。
   修复：改用分块读取以便重试，并禁用压缩（`Accept-Encoding: identity`，
   实测压缩正是截断诱因）。另加 256MB 响应上限，防止服务端异常时无限缓冲。

4. **主网钱包 + 测试网 API = 空结果。** 见上方"数据源设计"。

5. **测试桩缺少 EOF 信号会死循环。** 分块读取依赖 `read()` 返回空字节终止；
   一个永远返回数据的测试桩会让测试挂死。已修正测试并加响应体上限作为生产侧防御。

6. **持续性硬过滤会降低信号覆盖。** 见「聪明钱因子的选钱包逻辑」——
   把持续性从筛选条件改成权重，是这一轮改进里最反直觉但也最关键的结论。

7. **重启会清空所有护栏。** 当日次数、冷却、连亏熔断、持仓都只在内存里。
   已做持久化（见「护栏跨重启」）。

8. **`restore_payload` 只接受 dict，传对象会静默重置。** 传入 `AgentState`
   对象时 `data.get()` 抛 `AttributeError`，被兜底逻辑吞掉并返回全新状态 ——
   等于护栏又白存了。现在兼容 dict 与对象两种形态，并有专门的回归测试。

9. **配置在说谎。** `max_drawdown_pct` 和 `reduce_only_on_exit` 从未被任何代码引用。
   前者已实现，后者已删除并在文档里说明原因（退出走 `market_close`，
   本身就是 reduce-only，该开关只能是装饰）。

10. **未成交的挂单被当成成交。** 见「资金安全机制」第 2 条。

## 定时采集（cron）

公开 API **没有历史鲸鱼持仓接口**，所以「聪明钱因子能否回测」这件事完全取决于
从现在起积累多少历史。`scripts/collect.sh` 承担这件事，已注册为每 15 分钟一次的
cron 任务。

### 它做两件事

| 步骤 | 产物 | 用途 |
|---|---|---|
| `record_snapshots.py --symbols BTC,ETH` | `snapshots/whale_positions.jsonl` | 每个钱包的持仓 + 选币元数据，是日后回测 40% 因子的唯一数据源 |
| `run_bot.py --cycles 1` | `logs/journal.jsonl` | 一轮 dry-run 的信号、三因子明细、门禁拒绝原因、模拟订单 |

每次调用都是**新进程**，但会从 `logs/agent_state.json` 恢复持仓状态，所以累积下来的
journal 读起来是一段连续会话，而不是一堆互不相关的快照。

### 三个关键设计

**1. 加锁 —— 这个不能省。** 单次采集耗时约 60–160s，而间隔是 15 分钟。一旦某次
超时（比如网络抖动），下一次就会被锁立即拒绝，而不是两个进程同时拉取 37MB 排行榜
并同时往同一个 JSONL 和状态文件里写：

```
17:01:52 === start ===
17:02:04 SKIP: a previous collection run is still in progress   ← 锁生效
```

**2. 钱包缓存的 TTL 必须远大于轮询间隔。** 排行榜响应是 **37MB / 45,138 个账户**，
而采集的是"鲸鱼**持仓**"（每轮都刷新）。钱包**名单**是慢变量，没必要频繁拉。
实测：TTL 900s + 15 分钟轮询 ≈ **2.7 GB/天**；改成 6 小时 → **约 150 MB/天**，
信号新鲜度毫无损失。这就是 `WALLET_CACHE_TTL_SECONDS` 从 900 调成 6 小时的原因。

**3. 故障隔离。** 采集失败不能拖垮决策周期，反之亦然 —— 两个步骤各自记录退出码，
脚本最后以失败数作为退出码返回（cron 已设 `MAILTO=""`，避免无 MTA 时堆积邮件）。

### 每日汇总（IDE 自动化）

cron 负责采集，但**不会告诉你采到的数据是否健康**。为此配了一条 IDE 自动化
「采集每日汇总」，每天早上运行，产出简报：

- 快照覆盖度（条数 / 跨度 / 是否已可用）
- 决策日志的事件分布
- **采集节奏是否真的做到了**：统计 `=== start` 行数（完整一天应接近 96），
  并列出所有 `SKIP`（某轮超时占用了下一个间隔）与 `FAILED`
- 单轮耗时是否偏离常见的 60–160 秒
- **信号质量**（见下节）

> **匹配陷阱**：统计轮数必须用前缀 `grep -c '=== start'`。日志里真实的开始行是
> `=== start (symbols=BTC,ETH config=...) ===`，带参数 —— 用带结尾的
> `=== start ===` 去匹配会**恒返回 0**，让人误判成「采集从未运行」。这个坑
> 我在写提示词时踩过一次，已写进提示词本身防止被"优化"回去。

这条自动化是**只读**的：不改配置、不重启采集、不写文件。它的价值在于能发现
cron 自己不会报的问题 —— 比如"采集其实已经静默停了两天"，单看 cron 的退出码
是看不出来的（`collect.sh` 在锁竞争时会正常退出 0）。

调度：`FREQ=DAILY;BYHOUR=8;BYMINUTE=0`，按**本地时区**（UTC+8）解析 —— 已实测确认
下次运行落在本地早间而非 UTC 08:00（后者会是本地 16:00）。实际触发时间带有约
2 分钟的调度抖动（实测 07:57），对日报没有影响。

### 当前实测状态

- cron 在 `:00/:15/:30/:45` 准时触发（已验证 17:15:01 那一次完整跑通）
- 单轮耗时：冷启动 ~157s，热路径 ~83–108s，**占用率约 10–17%**
- 每轮约 190 次钱包读取（快照 92 + 决策 92）

### 关于「190 次钱包读取」：不改，但顺带修掉一个真 bug

两个脚本各自独立拉取同一批钱包持仓。**评估后决定不合并**，理由如下（均为实测）：

| 项 | 实测值 |
|---|---|
| 持仓读取耗时 | **51.8s** / 92 个钱包 |
| 每轮重复 | ×2 → 浪费约 52s |
| 占 900s 间隔 | **5.8%** |
| API 速率预算占用 | 全天约 **1%** |

另外实测了两次独立拉取（间隔 2 分钟）的数据：`long_ratio 61.4508` vs `61.45` —— **几乎逐位相同**，
因为鲸鱼持仓在分钟级是粘性的。所以连「两次拉取数据不一致」这个理由也不成立。

**为了省 5.8% 而把交易循环与数据采集耦合起来，是错的权衡。** 保持分离还带来真实的
故障隔离：采集失败不影响决策，反之亦然。

### 但排查过程中发现了一个真 bug：记录器无视配置

`SnapshotRecorder` 构造 `SmartMoneyFactor` 时**只用模块默认值，完全不读配置**。
默认值恰好等于出厂配置，所以一切看起来正常 —— 直到有人调整 `smart_money`：

```
把配置 top_per_window 改成 20:
  配置文件 top_per_window = 20
  记录器   top_per_window = 60   ← 不跟随
```

后果有两层：

1. **记录下来的快照描述的钱包集合不再是策略实际交易的那批** —— 而这份数据的唯一
   用途就是日后回测那个因子。数据错了，回测就失去意义。
2. `logs/smart_money_wallets.json` 的缓存签名包含这些参数 → 签名不匹配 →
   **变成两份缓存，每 6 小时下载两次 37MB**

修复：`SnapshotRecorder` 接受 `config`，并把选币参数**写入每条记录**作为溯源
（`selection` 字段）。这样未来回测能判断两段历史是否由同一套规则产生。

> 这个 bug 能藏住，是因为快照记录器的测试覆盖**为零**。现补 `tests/test_snapshots.py`（19 个用例）。

`--summary` 会直接告诉你：

```
NOT YET USABLE: 0.0 days of history. A smart money backtest needs months, not days.
```

按 15 分钟一轮计算，每天每币累积 **96 条**记录。**需要数月**才够支撑一次

### `--summary` 的三个部分

一条命令给出全部进展，日报直接消费它的输出：

```bash

```

1. **whale snapshots** —— 每币快照条数与跨度

## 回测（已跑，结论为负）

**先说结论：在可回测的那 60% 上，策略没有跑赢随机入场。** 这是 180 天真实数据
（2026-03-21 → 09-17，BTC）的结果：

| 对比项 | 结果 |
|---|---|
| 策略（3%/9% 出场） | **+0.20%** |
| 买入持有 | +8.94% |
| **同配置随机入场 ×50** | 均值 **+3.91%**（p5 +3.06% ~ p95 +4.76%）|
| 策略所处百分位 | **第 0 百分位** |

33 笔交易，胜率 36.4%，盈亏比约 1.8:1，profit factor 1.04 —— **勉强为正，
但低于同配置的随机入场**。

### 对照实验：所有配置都跑不赢自己的随机基准

| 配置 | 策略 | **同配置**随机基准 | 百分位 |
|---|---|---|---|
| 基准 3%/9% | +0.20% | +3.91% | **第 0** |
| **A 无固定止损（ATR 定仓）** | +0.33% | +4.23% | **第 0** |
| B 6%/18% | -1.48% | -1.73% | 第 84（仅 4 笔）|
| C 盈亏比 10:1（3%/30%） | -0.46% | — | — |

**每一个配置都落在各自随机基准的第 0 百分位。** 这是一个稳健的负面结论：
方向判断没有可证明的信息量。注意策略的绝对收益在「无固定止损」下会改善，
但**随机入场改善得更多**，所以百分位不动 —— 只看绝对收益会得出错误结论。

### 两个方法论要点

**1. 随机基准会随出场配置大幅漂移。** 同一份数据上，随机入场的均值在
+3.9% ↔ −1.7% 之间摆动，完全取决于止损/止盈设置。所以「是否跑赢随机」
**只能在同一配置内比较**；跨配置比百分位会得出完全相反的结论
（变体 B 单看是「第 84 百分位」，但它只有 4 笔交易）。

**2. 固定 3% 止损对 BTC 过窄。** BTC 的日常波动就能打穿 3%，止损被噪声反复触发。
改用 ATR 定仓后胜率从 36.4% 升到 38.7% —— 但百分位不变。

### 修复了一个保真度缺陷：反转平仓

回测原先**只在空仓时生成信号**，所以持仓只能靠止损/止盈退出。而实盘
（`agent/bot.py` 的 `run_cycle`）每轮都生成信号，遇到反向信号会**平仓并反手**。

修复前后的对比：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 净值 | -0.86% | **+0.20%** |
| 胜率 | 22.2% | **36.4%** |
| 每笔期望 | -0.32 | **+0.06** |
| 最大回撤 | 3.91% | **2.22%** |
| **信号评估次数** | **537** | **4287**（≈4320 根 bar）|

最后一行是关键：修复前 4320 根 bar 里只评估了 537 次信号 —— 不只是缺反转平仓，
连 `signals_seen` 和门禁拒绝统计都是错的。修复后门禁分布才有意义
（`threshold 3192 / already holding 939 / cooldown 73 / confidence 38 / halted 38`）。

**但这个修复没有改变结论** —— 百分位仍是第 0，因为随机基准同步上升。

### 必须说明的局限

- 样本小（33 / 31 / 4 笔），`metrics.py` 自己就会警告 <30 笔不具统计意义
- 180 天是**单一上涨行情**（买入持有 +8.94%）
- **40% 的鲸鱼因子是关闭的** —— 这测的是 60% 的模型，不是部署中的策略
- 配置里 `take_profit_pct: 9.0` 的注释写着「matching Fox's asymmetry」，但 Fox 的
  设计是**平均盈利 = 平均亏损的 10 倍**（43% 胜率即可盈利）。当前 3:1 需要 >25%
  胜率，实测 36.4% 虽已超过，但整体仍无边缘。**注释与所引设计不符。**

### 这些结论意味着什么

若可回测的 60% 没有边缘，那么整个策略的收益**完全押在那 40% 的鲸鱼因子上** ——
也就是证据最薄弱、还要等数月才能回测的那个部分。这不是「等数据」的理由，
而是「尽快验证全模型」的理由。

## 前向信号质量分析

`analyze_signals.py` 回答回测回答不了的问题：**live 信号（含鲸鱼因子）到底有没有预测力。**

它不需要等数月。按 96 个信号/天，**两周约 1300 个样本**就足以对「方向有没有信息量」
给出第一个读取。这正是它比回测更快的原因 —— 回测只能测 60%，而它测 100%。

```bash
python analyze_signals.py                          # 默认 1h/4h/24h 前瞻
python analyze_signals.py --horizons 4,12,48
python analyze_signals.py --max-gap-minutes 60     # 容忍更大的采集间隔
```

### 两个刻意分开的问题

**1. 信号能否预测？** —— 用**全部**信号测，包括被门禁拒绝的。这是更根本的问题，
所需样本也最少。中性信号不计入（它们本就没有方向），而不是当作猜错。

**2. 门禁是否过严？** —— 被拒绝的信号是一组**免费对照组**。如果被挡掉的信号事后
显著命中，说明门禁在挡有效信号。报告会按门禁归类给出各自的前瞻命中率。

### 几个实现细节

- **价格序列取自 journal 本身**（每条 signal 都记录了决策时刻的 mark price），
  所以不需要联网，也不可能与 agent 当时看到的价格不一致
- **前瞻价格必须落在目标时刻附近**（默认 ±30 分钟）才采用。采集会暂停、会漏跑，
  拿一个过期价格当前瞻收益会**凭空造出优势**
- **尚无前瞻数据的信号会被跳过**，而不是拿现有数据凑 —— 否则最近几根 bar 的
  涨跌会系统性污染结果
- **门禁原因先归一化再聚合**。原始文本带变量（`cooldown active, 239 min remaining`、
  `halted for another 187 min`），直接计数会让几乎每条独立成行，分布完全看不出来
- 报告会显式标注 `|z| >= 1.96` 才算 95% 置信，且 n<30 一律判为「样本不足」

## 回测

```bash
python run_backtest.py                        # 200 天，含基准对照
python run_backtest.py --days 90 --random-runs 100
python run_backtest.py --no-benchmark         # 只看策略
```

回测**复用真实的因子、纪律层与头寸计算**（`Synthesizer` / `Discipline` / `compute_size`），
不重新实现策略逻辑，避免两套代码漂移。

### 关键限制：聪明钱因子无法回测

公开 API 不提供历史鲸鱼持仓，所以**占 40% 权重、也是唯一有证据支撑的因子无法参与回测**。
回测会强制关闭 `require_smart_money_alignment`（否则 100% 信号被拦），
并在输出顶部和 CAVEATS 里明确标注。

**所以回测结果只反映剩下约 60% 的模型，不代表实盘策略。**

### 实测结果：跨币种交叉验证（200 天，$1,000 起始）

| 币种 | 收益 | 交易 | 胜率 | expR | PF | 买入持有 | 随机均值 | 随机分位 |
|---|---|---|---|---|---|---|---|---|
| BTC | **-2.40%** | 32 | 18.8% | -0.075 | 0.68 | +14.31% | +1.86% | 0 |
| ETH | +3.97% | 38 | 34.2% | +0.104 | 1.51 | +23.17% | +3.11% | 65 |
| SOL | +1.49% | 57 | 28.1% | +0.027 | 1.12 | +17.42% | -1.48% | 100 |

**结果在币种间不一致，且没有任何组合跑赢买入持有。**

### 出场结构的数学性质

止损 3% / 止盈 9%（盈亏比 3:1）时，随机游走下先触止盈的概率为
`3/(3+9) = 25%`，恰好等于打平所需胜率 —— **该结构在无方向信息时期望值精确为 0**，
计入成本后必为负。实测胜率在 18.8%-34.2% 之间围绕 25% 波动，与「无信息」一致。

### 因子消融：市场因子是负担

| 配置 | BTC | ETH | SOL |
|---|---|---|---|
| 技术+市场（当前） | -2.40% | +3.97% | +1.49% |
| **仅技术** | **+2.44%** | **+5.89%** | **+1.90%** |
| 仅市场 | 0.00%（0笔） | +0.27%（3笔） | +0.57%（2笔） |

仅技术在三币种上全部优于当前配置，说明**资金费率逆向因子在拖后腿**。

### 但该发现未通过样本外检验

把 200 天拆成前后两半，用「仅技术」配置：

| 币种 | 样本内胜率 / 盈亏 | 样本外胜率 / 盈亏 |
|---|---|---|
| BTC | 40.0% / +26.11 | 23.1% / **-1.69**（翻负） |
| ETH | 37.0% / +37.26 | 32.0% / +21.59 |
| SOL | 31.0% / +18.16 | 25.8% / **+0.81**（归零） |

样本外胜率收敛到 23-32%，即 25% 盈亏平衡点附近。**「仅技术更好」是样本内过拟合。**

### 资金费率套利也不成立

| 币种 | 均值 bp/h | 年化 APR | >0 占比 |
|---|---|---|---|
| BTC | 0.051 | **4.5%** | 75.7% |
| ETH | 0.059 | **5.1%** | 78.9% |
| SOL | -0.014 | **-1.2%** | 57.2% |

delta 中性需 50/50 分配资金，净年化仅约 **2-2.5%**，且承担基差、强平与交易所风险。

### 突破：聪明钱历史可以被重建

最初结论是「聪明钱因子无法回测，需等数月快照」。**这是错的** —— 我只查了
`clearinghouseState`（仅当前状态），漏掉了历史端点。

`userFunding` 的每条记录都带 `szi`（当时的持仓数量）：

```json
{"time": 1771891200000, "delta": {"coin":"ETH","szi":"-5.7725625","fundingRate":"0.0000090922"}}
```

用它 + 游标分页，可以重建每个钱包的历史持仓序列：

```bash
# 采集（约 3-4 分钟，250 个候选账户）
# 内置于 backtest/whale_history.py
```

**实测采集结果**：87-103 个钱包可用，10,612 个持仓点，覆盖 2025-08 → 2026-09（13 个月）。

### 数据粒度的真相

**关键发现**：funding 记录是**日级**，不是小时级（中位间隔 24h，仅 41% 间隔 ≤6h）。
这直接决定样本量：

| 陈旧窗口 | 平均持仓钱包数 | 有数据的时间占比 |
|---|---|---|
| 6h | 1.3 | **仅 12%** ← 不可用 |
| 24h | **21.6** | 100% |
| 48h | 23.9 | 100% |

之前观察到的「越陈旧越好」不是陈旧起作用，而是**覆盖率**：6h 时因子基本处于
「无数据」状态。

交易数从 32→24、38→30、57→42 都在下降。**如果基础信号是负期望的，任何减少交易的
过滤都会「改善」结果**，那就不说明聪明钱有信息量。用**随机同意/反对**的顾问
替换聪明钱意见（相同门禁、相同结构）作为对照：

| 币种 | 真实聪明钱 expR | 随机顾问 expR |
|---|---|---|
| BTC | **+0.121** | -0.014 |
| ETH | **+0.086** | +0.072 |
| SOL | **+0.089** | +0.030 |

**每笔期望值 3/3 优于随机顾问** —— 说明是信息量而非交易数减少。
但 ETH 的总收益随机顾问反而更高（+3.62% vs +2.84%），且 ETH 的 expR 差距在噪声内。

### 结论：是目前唯一的正向线索，但未证实

支持它的证据：跨 3 币种一致、样本外保持、随机方向分位高、每笔期望值优于随机顾问。

**仍不足以支撑实盘**：

1. **不显著**：随机分位 90/93/100% 在 30 次采样下约 p 0.03-0.10，
   且经过多轮比较后削弱
2. **回测的不是要跑的东西**：回测用 24h 陈旧持仓，线上读**实时**持仓
3. **样本小**：每币种仅 24-42 笔，单周期
4. **覆盖率不完整**：BTC 103 / ETH 62 / SOL 73（候选 250）

### 总结论（最终）

| 方向 | 结论 |
|---|---|
| 技术 + 资金费率方向预测 | 无 edge，样本外不成立 |
| 市场因子（资金费率逆向） | 有害，拖累表现 |
| 资金费率套利 | 净约 2% APR，不值得 |
| **聪明钱因子** | **唯一正向线索，跨币种一致，但未证实** |

**不建议实盘。** 唯一合理的下一步是让 Agent 以 dry-run 跑起来积累
**实时**信号的验证记录 —— 因为线上数据（实时持仓）严格优于回测数据（24h 陈旧），
而这是回测无法回答的部分。

### 数据边界

| 数据 | 可用范围 |
|---|---|
| 1h K 线 | 约 **208 天**（受 5000 根上限约束） |
| 4h K 线 | 1 年以上 |
| 每小时资金费率 | 与 K 线同期 |
| 历史 OI / 鲸鱼持仓 | **不存在** |

### 为将来铺路：快照采集

python record_snapshots.py                # 采集 BTC+ETH 鲸鱼持仓
